자율체인(auto-chain) 운영 가이드

여러 세션이 걸리는 큰 작업을 Claude Code가 계획, 검토, 병렬 구현, 다음 세션 인계까지 스스로 이어가게 하는 방식입니다. 왜 만들었는지, 무엇이 필요한지, 실제로 어떻게 돌아가는지, 프로젝트마다 다른 마감 절차는 어디서 정하는지를 다이어그램과 함께 정리했습니다.

1한눈에 보기

사용자가 목표를 주고 "자율체인으로 진행해"라고 하면 이렇게 진행됩니다.

  1. 계획 세션: 권한을 한 번 확인합니다. Opus가 작업을 마일스톤 → 웨이브 → task로 나눈 계획을 쓰고, 다른 계열 모델(GPT-6.1 Sol)이 그 계획을 검토합니다.
  2. 마일스톤 세션: 마일스톤마다 새 Claude Code 세션이 Orca 탭으로 열립니다. 이 세션은 조정만 합니다. 구현은 Sonnet worker들이 병렬로 하고, 커밋은 조정자가 하나씩 합니다.
  3. 마감: 전체 시험을 돌리고 Sol 최종 검토를 받은 뒤, 상태 파일을 남기고 다음 마일스톤 탭을 엽니다.
  4. 프로젝트별 추가 절차: 리포의 .claude/autonomous-chain.md 프로파일에 적어 두면, 정해진 시점마다 공통 절차 다음에 실행됩니다.

계획은 Opus

되돌리기 어려운 설계면 xhigh, 그 밖에는 high.

검토는 Sol

OpenCode review-sol을 Orca 탭에서 실행합니다. 구현한 모델과 다른 계열이 검토합니다.

구현은 Sonnet

task마다 worker 하나를 병렬로 띄웁니다. 판단이 필요한 task만 Opus가 맡습니다.

세션 사이는 파일로

대화 기억 대신 state.md가 진행 상황을 이어받게 합니다.

2왜 만들었나

여러 날, 여러 세션이 걸리는 작업을 한 세션에서 끝까지 끌고 가면 세 가지 문제가 생겼습니다.

문제원인자율체인의 대응
비용이 빠르게 늘어남매 턴마다 지금까지의 대화 전체를 다시 읽습니다. 그래서 비용은 대략 컨텍스트 크기 × 남은 턴 수로, 세션 길이에 대해 제곱으로 늘어납니다.마일스톤마다 세션을 새로 엽니다. 조정자는 worker의 코드를 읽지 않고 한 줄 보고만 받습니다.
사람이 붙어 있어야 진행됨질문이 생길 때마다 멈추고, 다음 세션은 사람이 직접 열어야 했습니다.기술 선택은 추천안으로 정해 진행하고 질문 대기열에 적어 둡니다. 다음 세션은 Orca 탭으로 자동으로 엽니다.
자기 검토의 맹점같은 모델이 구현하고 검토하면 같은 지점을 놓치기 쉽습니다.계획 검토와 마일스톤 최종 검토를 다른 계열 모델(GPT-6.1 Sol)이 맡습니다.

설계 목표

  • 조정자(오케스트레이터) 세션의 컨텍스트를 최소로 유지합니다.
  • 작업 크기에 맞게 실행 방식을 고릅니다. 작은 수정은 직접 하고, 독립 단위가 여럿이면 병렬 worker에 맡깁니다.
  • 질문이 생겨도 멈추지 않고 다음 마일스톤까지 이어갑니다. 멈추는 경우는 따로 정해 둡니다.
  • task, 웨이브, 마일스톤이 끝난 뒤 할 일은 프로젝트마다 다르게 정할 수 있게 합니다.

하지 않는 것

  • 프로젝트별 진행 도구(원장, 사내 시스템 동기화 등)를 스킬이 직접 구현하지 않습니다. 프로파일은 그런 도구를 가리키기만 합니다.
  • 구현은 Claude만 합니다. 다른 모델로 구현을 재시도하는 단계는 두지 않습니다.
  • 작은 수정이나 질문에는 쓰지 않습니다. 이런 일에는 검토 비용이 더 큽니다.
출처OpenCode용 autonomous-chain 스킬 v2(질문 분류, 검증 예산, BLOCK 범위 한정, 재개할 때 다시 계획하지 않기)와 GIRA 프로젝트의 Kiro 실행 방식(마일스톤 세션과 task 서브에이전트, 조정자는 코드를 읽지 않음, 보고서 형식)을 합쳐 Claude Code용으로 다시 설계했습니다.

4구성 요소와 모델

역할에이전트모델 · effort쓰는 경우
계획chain-plannerOpus · high기본

구현(판단)chain-worker-deepOpus · high상태·동시성·권한 경계, 원인 조사가 핵심일 때. chain-worker가 실패한 뒤 재시도할 때
검토OpenCode review-sol (Orca 탭)GPT-6.1 Sol · high계획 검토, 웨이브 고위험 검토, 마일스톤 최종 검토
조정메인 세션세션 모델마일스톤 조정, 커밋, 기록, 통합 검증, 인계
  • 모델과 effort는 에이전트 정의 파일 frontmatter에 고정돼 있습니다. 호출할 때 덮어쓰지 않습니다. 호출 이름에는 플러그인 접두사를 붙입니다(auto-chain:chain-worker).
  • worker 등급은 planner가 task마다 근거와 함께 정합니다. "중요해 보인다"는 이유만으로 올리지 않습니다.
  • worker 정의에는 Agent 도구가 없습니다. worker가 서브에이전트를 다시 만들 수 없습니다.

단위정의끝날 때
마일스톤결과를 관찰할 수 있는 통합 지점입니다. 관찰 가능한 종료 조건이 있고, 세션 하나가 처음부터 마감까지 조정할 수 있는 크기로 나눕니다.전체 검증 → Sol 최종 검토(무거움) → wrap-up → 다음 마일스톤 탭
웨이브동시에 진행할 수 있는 task 묶음입니다. 소유 파일이 겹치는 task는 다른 웨이브로 나눕니다.전체 검증 1회 → 고위험 task가 있으면 Sol 검토(가벼움) → push(권한이 있을 때)
taskworker 한 세션 안에 끝나는 크기입니다. 인수 기준은 "명령 Y가 Z를 출력한다"처럼 관찰 가능한 결과로 씁니다.worker의 영향 시험 → 보고서 → 조정자 커밋

task마다 계획 문서에 worker 등급, high-risk 여부, owns(소유 파일), ac(인수 기준), verify(영향 시험 명령), deps(선행 task)를 적습니다. 카탈로그, 라우트 표, 버전 파일처럼 여러 task가 함께 고치는 공용 파일은 조정자 소유로 따로 빼고, worker는 보고서에 "등록 요청"만 적습니다.

6전체 흐름

체인은 계획 세션 1개와 마일스톤 세션 N개로 이뤄집니다. 세션끼리는 대화를 넘기지 않습니다. 상태 파일과 인계 문서 두 파일만 넘깁니다.

sequenceDiagram
  autonumber
  actor U as 사용자
  participant P as 계획 세션
  participant PL as chain-planner
  participant SOL as Sol 탭
  participant M1 as M1 세션
  participant M2 as M2 세션
  U->>P: 목표 + 자율체인으로 진행해
  P->>U: 권한 확인 1회 (커밋 / push / 외부 쓰기 / 새 비용)
  U-->>P: 허용 범위
  P->>PL: 목표, authority, 프로파일 경로
  PL-->>P: plan.md
  P->>SOL: 계획 검토 요청 (snapshot + nonce)
  SOL-->>P: 판정 SHIP 또는 BLOCK
  Note over P: BLOCK이면 planner에 delta 수정 후 재검토 (최대 3회)
  P->>P: state.md, questions.md 생성 + 인계 문서
  P->>M1: Orca 탭 기동 + 한 줄 프롬프트
  Note over M1: 마일스톤 세션 절차 (그림 4)
  M1->>SOL: 마일스톤 최종 검토
  SOL-->>M1: SHIP
  M1->>M2: Orca 탭 기동 + 한 줄 프롬프트
  M2->>M1: 부모 탭 close (child가 닫음)
  Note over M2: state.md를 승계해 계획 없이 M2부터
  M2-->>U: 마지막 마일스톤이면 종료 보고 + 질문 대기열 요약
계획 직후 M1을 같은 세션에서 해도 되나됩니다(1.1.0부터). 계획 세션에 맥락이 충분히 남아 있으면 M1을 이어서 진행하고, 인계는 M1→M2부터 합니다. 그렇게 했다는 사실을 상태 파일의 "결정"에 남깁니다.

실행 단계 고르기

단계언제실행
직접결과가 뻔하고, 어차피 코드를 봐야 판정할 수 있는 작은 수정조정자가 직접 고치고 영향 시험
병렬파일 소유를 나눌 수 있는 독립 단위가 2개 이상worker 서브에이전트에 맡김
체인여러 세션 분량, 큰 설계 판단, 또는 사용자가 명시 요청계획 세션 → 마일스톤 세션들

파일 수 같은 숫자 기준은 두지 않습니다. 판단이 애매하면 가벼운 쪽을 고릅니다.

7마일스톤 세션 내부

마일스톤 세션의 메인 Claude는 조정자입니다. 구현은 하지 않고 띄우기, 커밋, 검증, 기록, 인계만 합니다. 주황색 상자는 프로젝트 프로파일의 훅이 끼어드는 시점입니다(11절).

worker에게 넘기는 것

계획 전문은 붙이지 않고 다음만 넘깁니다. worker는 필요한 절을 파일에서 직접 읽습니다.

  • 공통 지시서 references/task-brief.md의 절대 경로(프로파일에 task-brief가 있으면 그 경로도)
  • 리포 절대 경로, 계획 문서 경로와 task 위치(예: M1-W1-T03)
  • 관련 결정 번호, 고위험 여부
  • 보고서 경로 docs/chain/<chain-id>/reports/<task-id>.md

worker는 <보고서 경로> — <결과> <요약> 한 줄만 돌려줍니다. 조정자는 diff를 읽지 않습니다.

검증 예산

시점실행하지 않음
task 완료worker가 영향 시험조정자의 재실행
웨이브 통합verify.static(있으면) → verify.full 1회. 실패하면 원인 task에 수정 worker를 1회 보내고, 실패 항목과 영향 시험만 다시 돌림통과한 항목 재실행
마일스톤 마감verify.full 1회. 같은 snapshot의 웨이브 통합 결과가 있으면 재사용증거 시험을 처음부터 다시
통과가 아닌 것수집 0건, skip, 미실행, timeout, 빈 응답은 통과로 세지 않습니다. 시험 결과는 총계(실행 수 · skip 수)와 함께 기록합니다.

8조정자와 worker의 역할 분리

핵심 규칙은 하나입니다. git index에 쓰는 작업은 조정자만 합니다. 경로를 지정한 커밋도 index 전체를 잠그기 때문에, worker 여럿이 동시에 커밋하면 index.lock 충돌이 납니다.

공용 파일 · 상태 파일 · 질문 대기열조정자만 수정보고서에 "등록 요청"으로만 적음
서브에이전트worker · planner 기동만들 수 없음
  • 보고서의 변경 목록과 git status 이름 목록이 다르면, 목록 밖의 파일은 커밋하지 않습니다. 내용을 읽지 않고 질문 대기열에 올립니다.
  • 보고서 파일 자신은 변경 목록에 넣지 않습니다. 조정자가 task 커밋에 함께 넣습니다.
  • authority에 로컬 커밋이 없으면 커밋하지 않습니다. 커밋할 경로를 상태 파일에 쌓아 두고, 검토에는 HEAD와 함께 작업 트리 식별자를 씁니다.

9Sol 검토 게이트

검토는 OpenCode의 review-sol 에이전트가 Orca 탭에서 읽기 전용으로 합니다. 결과 파일은 쓰지 않고 터미널 출력으로 받습니다. 조정자는 그 출력이 로그 파일로 남도록 해 두고, 로그에서 판정을 꺼냅니다.

게이트대상조건무게 · 회차
계획전체 계획계획 review: required마일스톤 2개 이상이면 무거움 3회, 1개면 가벼움 1회
웨이브 통합그 웨이브의 고위험 task 변경고위험 task가 있을 때, push 전가벼움 1회
마일스톤 마감마일스톤 전체 변경, 종료 조건, 실행 증거항상무거움 최대 3회

무거운 게이트

재검토 요청에 회차(round 2/3)를 적습니다. 같은 finding이 두 번 연속 나오면 근거를 붙여 1회 반박할 수 있습니다. 3회 뒤에도 BLOCK이면 통과로 처리하지 않고 멈춥니다.

가벼운 게이트

리뷰 1회 → BLOCK 수정 → 영향 시험으로 확인 → 재검토 없이 진행합니다. 수정한 항목은 마일스톤 최종 검토 범위에 넣습니다.

BLOCK의 범위

구체적 오동작, 요구 누락, 중대한 회귀, 권한·데이터 오류, 핵심 검증 누락만 BLOCK입니다. 취향이나 문서 형식은 NOTE입니다.

왜 nonce를 쓰나리뷰어는 이전 회차 로그를 인용하거나, 명령을 시험하면서 REVIEW-DONE이나 판정: SHIP 같은 문자열을 직접 출력하기도 합니다. 단순 grep으로는 이번 회차의 종료와 구분할 수 없습니다. 그래서 요청 파일 해시로 만든 nonce 표식 줄 하나만 완료 신호로 씁니다.
작업 트리 식별자미커밋 변경과 새 파일 내용을 해시한 값입니다. 검토 절차가 스스로 쓰는 파일(reviews/, state.md, questions.md)은 빼고 계산합니다. 그래서 검토 중에 상태 파일을 갱신해도 값이 바뀌지 않고, 리뷰어가 제품 파일을 건드렸을 때만 달라집니다.

Sol을 쓸 수 없을 때

  • 웨이브 고위험 검토: Opus 보조 검토로 진행합니다. 해당 task를 sol-pending으로 표시하고 마일스톤 최종 검토 범위에 반드시 넣습니다.
  • 계획 검토 · 마일스톤 최종 검토: 다른 리뷰어로 대신하지 않습니다. unverified로 두고 멈춥니다(멈춤 조건 5).

10권한 · 질문 · 멈춤

권한(authority)

계획 세션에서 딱 한 번 네 가지를 확인하고 state.md의 authority에 기록합니다.

authority: { local-commit: yes|no, push: none|wave|milestone, external-write: no|<범위>, new-cost: no|<범위> }
권한은 늘어나지 않습니다스킬의 기본값, Sol의 SHIP 판정, 추천안 선택은 새 승인을 만들지 않습니다. 처음에 허용한 범위가 체인이 혼자 할 수 있는 상한입니다. 프로파일에 commit·push가 있으면 사용자가 미리 정해 둔 정책으로 보고 다시 묻지 않습니다.

멈추는 경우 (이때만)

2같은 task가 재시도와 조정자 직접 마무리 뒤에도 실패

11프로젝트 프로파일과 훅

모든 프로젝트에 같은 절차는 스킬에 있습니다. 프로젝트마다 다른 일(검증 명령, 마감 때 원장 갱신, 사내 시스템 동기화 같은 것)은 대상 리포 루트의 .claude/autonomous-chain.md 한 파일에서 정합니다. 파일이 없으면 기본값으로 동작합니다.

## on-milestone-close
- 패치 버전을 올리고 `npm run build`가 통과하는지 확인한다.
- `CHANGELOG.md`에 마일스톤 요약 3줄을 추가한다.

## high-risk
- `src/auth/**`, `db/migrations/**` 변경

## stop-conditions
- 운영 환경 자격증명이 필요해지면 멈춘다.

Orca 탭 인계

sequenceDiagram
  participant A as 이전 세션 (부모)
  participant O as Orca
  participant B as 새 세션 (child)
  A->>A: 마감 · wrap-up · 인계 문서 작성 (부모 handle 기재)
  A->>O: terminal create (인계 시도당 1회)
  O-->>A: handle
  A->>O: wait tui-idle → read --screen 으로 기동 확인
  A->>O: send 한 줄 프롬프트 (상태 파일 + 인계 문서 경로)
  A->>O: read --screen 으로 수신 확인 (이후 감시하지 않음)
  O->>B: 프롬프트 전달
  B->>B: 인계 문서 · state.md 읽기
  B->>O: terminal close 부모 탭 (child가 닫음)
  O-->>B: ok, ptyKilled 값
  B->>B: ptyKilled false면 terminal list로 제거 확인 후 기록
  B->>B: current 위치부터 진행
  • 프롬프트는 줄바꿈 없는 한 줄입니다. 여러 줄을 보내면 줄바꿈이 Enter로 처리돼 중간에 제출됩니다. 긴 지시는 인계 문서에 적고, 프롬프트에는 경로만 넣습니다.
  • 새 worktree를 만들지 않고 같은 신뢰 폴더에 탭을 엽니다. 한 worktree에는 한 시점에 편집 소유자를 한 명만 둡니다.
  • 부모 탭은 자기 자신이 아니라 child가 닫습니다. 부모가 스스로 닫으면 실행 중인 명령이 끊길 수 있기 때문입니다.
  • 맥락이 부족해지면 마일스톤 도중이라도 안전한 지점에서 인계할 수 있습니다. 진행 중인 worker나 리뷰가 있으면 결과 회수 책임을 인계 문서에 적습니다.

13사용법

시작

새 Claude Code 세션(Orca에 등록된 폴더에서 연 세션)에서 목표와 함께 지시합니다.

자율체인으로 진행해.
목표: MDS의 Nexacro 화면 추출 역량을 추가 (XFDL 파싱 → 화면 카탈로그 → 웹 표시)
완료 기준: MDS 화면 목록이 웹에 보이고 전체 시험 통과
권한: 로컬 커밋 OK, push는 하지 마

"자율체인으로 진행해"라는 말이 스킬을 부릅니다. 직접 부를 수도 있습니다: Skill(auto-chain:autonomous-chain). 완료 기준을 빼면 planner가 정하고 계획 문서에 남깁니다. 권한을 빼면 시작할 때 한 번 묻습니다.

중간에 끊겼을 때

<리포>/docs/chain/<id>/state.md 를 읽고 auto-chain 스킬로 이어서 진행해.

끝난 뒤 볼 것

  • state.md: 무엇을 했고 어떤 검증과 검토를 통과했는지
  • questions.md: 체인이 추천안으로 정하고 넘어간 것, 권한 때문에 보류한 것

쓰지 않는 게 나은 경우

버그 하나 수정, 문구 변경, 질문, 범위가 닫힌 작은 기능은 평소처럼 지시하는 편이 빠릅니다. 체인은 계획 검토와 마일스톤 검토가 붙어 작은 일에는 오히려 느립니다.

14실사용 시험 결과 (trial-1)

2026-10-23에 시험 리포 chain-trial에서 계획 → M1(병렬 task 3개) → M2(CLI 통합 task 1개)를 끝까지 돌렸습니다.

찾아서 1.1.0에 반영한 결함

  • K1 worker마다 보고서 파일 자신을 변경 목록에 넣는 방식이 달랐습니다 → "넣지 않는다, 조정자가 함께 커밋한다"로 고정했습니다.
  • K2 계획 세션이 M1까지 이어서 해도 되는지 정해져 있지 않았습니다 → 맥락이 충분하면 허용합니다.
  • K3 Orca에 등록되지 않은 리포는 인계 탭도 등록된 worktree에 열어야 했습니다 → 인계 절에 명시했습니다.
  • K4 부모 탭을 닫을 때 ok: true인데 ptyKilled: false인 경우를 다루지 않았습니다 → 값을 기록하고 terminal list로 제거를 확인합니다.
  • 플러그인 이름 claude- 접두사가 예약어 규칙에 걸려 auto-chain으로 바꿨습니다.
