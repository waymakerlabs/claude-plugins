자율체인과 리뷰체인

큰 작업은 자율체인이 마일스톤 단위로 끝까지 밀고 가고, 끝난 뒤 사람이 화면을 보며 쏟아내는 수정사항은 리뷰체인이 병렬로 받아 처리합니다. 두 체인은 같은 터미널 계층(agent-orchestrator) 위에서 돌고, 세션끼리는 받은편지함 파일로만 말합니다.

실행 3단계 (§1-1)

단계쓰는 작업
① 기본 Agent웨이브 구현 task, BLOCK 수정, 전수 점검, 조사, chain-breaker
② headlessSol 검토(review-run.sh), 다른 CLI 실행(headless-run.sh) + done 파일
③ pane최초 계획, 인계를 넘겨 사는 planner, 마일스톤 인계, 사용자가 지켜볼 작업

③에서 10·11·12를 받으면 ①·②로 내려갑니다. ①로 내려간 작업은 인계 전에 현재 세션에서 회수합니다.

상태 파일

docs/chain/<chain-id>/state.md가 세션 사이를 잇습니다. 질문 대기열·결함 계열 원장·백로그가 옆에 있습니다.

롤링 분해

최초 계획은 골격 + 첫 두 마일스톤만 분해. Mn 마감 때 Mn+2를 chain-planner가 분해합니다.

조정자 규율

보고서 + 실제 diff + 위험 지점만 봅니다. git index 쓰기는 조정자만, 커밋은 하나씩 경로 지정.

세는 것

PARTIAL·BLOCKED·보고서 없음, 고쳤는데 같은 증상(같은 결함 계열 포함), 원인 가설이 빗나감.

세지 않는 것

오타·빠진 import·경로, flaky 의심(1회 재실행), index.lock·포트·오래된 빌드, API 재시도 반복, 진단은 맞고 구현만 틀린 경우.

지시서 항목: 리포·HEAD·금지 파일 / 재현 명령 / 통과·실패 커밋 / 확인된 사실 / 의심 지점 / 반박된 가설 전부 / 금지(대기 늘리기·시험 완화·우회) / 시험 명령 / 보고 형식.

  OC->>OC: merge.lock → SHA 고정(rev-parse 대조)
  OC->>OC: 범위 확인: diff 파일 ⊂ 선점 · 시험 삭제 직접 확인
  OC->>A: git diff main...SHA 정독
  A-->>OC: OK | CONCERN 한 줄
  OC->>M: merge --ff-only SHA
  OC->>M: verify.merge 1회 → 공용 파일 커밋 → push(권한 있을 때)
  OC->>W: [닫기] / 다른 worker에 [main갱신]

worker 커밋 예외

worktree마다 index가 따로라 index.lock이 겹치지 않습니다. 전역 "git index 쓰기는 메인만"의 승인된 예외(2026-11-09, D5). authority.worker-commit: no면 OC가 대신 커밋.

merge.lock

모든 끝 경로에서 지웁니다. 예외는 병합 뒤 verify.merge 실패 하나 — lock을 남겨 다른 병합을 막고 보고합니다.

정리

ignored 데이터 사본을 먼저 archive/로 옮긴 뒤 git worktree remove(--force 금지), 브랜치는 -d.

herdr 어댑터

  • HERDR_ENV=1이 아니면 11. 실측 기준 herdr 0.9.5.
  • tab create·pane split에 항상 --no-focus. worker pane은 오른쪽 열에 위아래로, 최대 5개, 넘치면 넘침 탭.
  • --confirm = working 또는 done 관측까지 최대 60초.
  • 받은편지함 대상: 절대 경로(*.log) 또는 pane id → ~/.local/state/agent-orchestrator/inbox/pane-<id>.log. 받은편지함 종료 코드는 0 / 2 / 4.

14세션 간 메시지 원칙 (2.6.0)

이미 첫 지시를 받은 세션의 입력창에는 아무것도 쳐 넣지 않는다.agent-send는 새 세션의 첫 지시 시도 1회뿐입니다. "유휴일 때만", "사용자가 치지 않을 때만" 같은 예외도 없습니다. 미제출 초안이 남아 있을 수 있고, 확인과 전송 사이에 사용자가 칠 수 있기 때문입니다.

계기

회사 프로젝트에서 자율체인 M2 조정자가 체인을 띄운 부모 [OC] 세션에 agent-send로 답을 보내, 사용자가 쓰던 입력창에 메시지가 들어갔습니다. 당시 받은편지함 방식은 review-chain 0.1.2에만 있었습니다.

해결

auto-chain 2.6.0 · review-chain 0.1.4 · agent-orchestrator inbox-send/inbox-watch(커밋 b3dcb2d~950f04d).

sequenceDiagram
  participant S as 보내는 세션
  participant F as 받은편지함 .log
  participant R as 받는 세션 (Monitor)
  S->>F: inbox-send 대상 "한 줄" (flock 잠금 아래 덧붙임)
  F-->>R: inbox-watch → "#n 원문" 알림
  R->>R: 보고로 처리 (승인 아님)
  R->>F: inbox-watch --ack 대상 n
  Note over R: 만료 알림이 오면 같은 명령으로 다시 건다
재개·인계 직후에는 --pending
장치내용
받은편지함 + MonitorMonitor command: "$AO" inbox-watch <대상>, timeout_ms: 1800000. 메시지 머리 [worker <이름>] <done|failed|question|blocked> <보고서> <한 줄>
체인 고정 조정자 주소~/.local/state/agent-orchestrator/inbox/chain-<chain-id>/coordinator.log. 인계로 pane이 바뀌어도 보고가 새 조정자에게 갑니다. ③ worker는 worker-<이름>.log, 부모·일반 메인은 pane id 받은편지함
인계 동결옛 소비자가 Monitor 중지 → --ack → 인계 문서에 "받은편지함 동결 · 마지막 ack n" → 그 뒤 첫 지시. 소비자가 바뀌면 이전 세션 미처리 줄은 #0 [이전 세션 …] 보류로 표시되고, 사용자 확인 뒤 --release
flock 잠금처음 판의 mkdir 잠금 + 복구는 복구자가 새 소유자의 잠금을 지우는 경쟁이 있었습니다(완료 검토 BLOCK). /usr/bin/perl로 상속 fd에 커널 flock을 걸어, 죽은 소유자의 잠금은 커널이 풉니다. 약 10초 못 잡으면 4
정지 재지시agent-keys <이름> Escape(입력창에는 아무것도 치지 않음) 뒤 worker 받은편지함에 inbox-send
