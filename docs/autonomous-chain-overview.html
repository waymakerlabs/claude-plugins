자율체인(auto-chain) 개요

대상: 이 환경을 처음 보는 개발자 · 기준: auto-chain 2.3.0 스킬 문서와 agent-orchestrator 계약 문서

자율체인은 여러 세션 분량의 큰 작업을 Claude Code가 사람 개입을 최소로 하며 끝까지 진행하게 하는 스킬이다. 작업을 마일스톤 → 웨이브 → task로 나누고, 마일스톤 하나를 조정자 세션 하나가 맡는다. 계획은 Opus 계획 에이전트가 쓰고, 검토는 다른 계열 모델(GPT-6.1 Sol)이 맡으며, 구현은 Claude worker가 병렬로 한다. 마일스톤이 끝나면 조정자는 상태 파일과 인계 문서를 남기고 새 세션을 열어 다음 마일스톤을 넘긴다. 모든 프로젝트에 공통인 절차는 스킬이 정하고, 프로젝트마다 다른 검증 명령·권한·추가 절차는 프로젝트 프로파일 파일이 정한다.

1. 구조 — 무엇으로 이뤄지는가

자율체인은 Claude Code 플러그인(auto-chain) 하나로 배포된다. 플러그인 안에는 절차를 담은 스킬 autonomous-chain, 역할별 에이전트 정의 6개, 참고 문서(계획 지침·worker 공통 지시서·리뷰 절차·프로파일 형식·pane worker 절차), 실행 스크립트가 들어 있다. 여기에 플러그인 밖 공용 도구 agent-orchestrator가 터미널 오케스트레이션 툴을 감춘다.

1-1. 작업 단위: 마일스톤·웨이브·task

  • 체인: 하나의 큰 목표. 계획 세션 1개와 마일스톤 세션 여러 개로 진행된다. 체인마다 chain-id가 있고 산출물은 docs/chain/<chain-id>/에 모인다.
  • 마일스톤: 세션 하나가 조정하는 단위. 종료 조건, 모드(build 구현 모드 / harden 출시 검토), 등급(화면 / 데이터), 마감 게이트 무게(light / heavy)를 가진다.
  • 웨이브: 마일스톤 안에서 동시에 돌릴 수 있는 task 묶음. 소유 파일이 겹치지 않는 task만 같은 웨이브에서 병렬로 돈다(상한 parallel-max, 기본 3). 웨이브가 끝나면 통합 검증을 한 번 한다.
  • task: worker 하나가 구현하는 단위. 계획에 worker 등급·고위험 여부·소유 파일·인수 기준(AC)·검증 명령이 표시된다. id는 M1-W2-T05 형태다.

최초 계획은 두 층이다. 전체 마일스톤 골격과 마일스톤을 가로지르는 결정, 그리고 첫 두 마일스톤의 task 분해만 쓴다. 이후에는 Mn의 마지막 웨이브를 띄운 직후 Mn+2를 분해하는 롤링 분해로 계획이 늘 한 마일스톤 앞서 있게 한다.

1-2. 역할과 모델 등급

역할마다 기본 모델과 effort가 정해져 있다. worker 등급은 planner가 task마다 표시한 대로 따르고, "중요해 보인다"는 이유로 올리지 않는다. worker는 서브에이전트를 다시 만들 수 없다(정의에서 Agent 도구가 빠져 있다).

역할에이전트모델 · effort쓰는 경우
조정자메인 세션세션 모델마일스톤 조정, 커밋, 기록, 통합 검증

파괴 검토chain-breakerOpus · high기본 끔. 켜면 BLOCK 수정 뒤 리뷰와 동시에 "방금 수정이 깨뜨린 곳"을 재현으로 찾는다. 리포에 쓰지 않는다

조정자의 규율은 단순하다. worker 보고서와 실제 diff, 그리고 보고서가 가리킨 위험 지점만 본다. diff 밖의 worker 코드는 읽지 않고, worker가 통과시킨 시험을 task마다 다시 돌리지 않는다. git index에 쓰는 작업(add·commit)은 조정자만 한다. worker 여럿이 커밋하면 index.lock이 충돌하기 때문이다.

1-3. 상태 파일·질문 대기열·보고서

체인은 세션을 여러 번 바꿔 가며 진행되므로, 기억은 파일에만 둔다.

파일쓰는 사람담는 것
plan.mdplanner목표·범위·핵심 결정, 마일스톤·웨이브·task 절(AC·소유 파일·등급·고위험 표시)
state.md조정자만frontmatter(현재 위치, authority, 검증 명령, 리뷰어, 백엔드, 스킬 버전) + 마일스톤 표, 진행 표, 검증 기록, 리뷰 기록, 결정, 미해결, 모델 적용 확인, 시간
questions.md조정자만질문 대기열. 질문, 추천안, 실제 택한 선택(또는 "대기"), 되돌리는 비용
reports/<task-id>.mdworker결과, 변경 파일 목록, 실행한 시험, 후속·주의, - 진행: 줄(감시용)
defect-classes.md조정자만결함 계열 원장. BLOCK을 근본 원인 패턴별로 묶어 "올바른 모양"을 다음 worker 지시서와 리뷰 요청에 넣는다
backlog.md조정자만구현 모드에서 미룬 경계 조건 결함, [30분]·[quarantine] 항목
reviews/조정자리뷰 판정 결과 파일(리뷰 중에는 /tmp에 두고 판정 뒤 옮긴다)

상태 파일의 "## 시간" 절에는 마일스톤 마감마다 계획·구현·리뷰 실행·회수 대기·수정·재검증·사람 대기·죽은 시간을 분 단위로 한 줄 남긴다. 실측이 아닌 값에는 U를 붙인다. 절차 변경의 효과를 재기 위한 장치다.

1-4. 리뷰 게이트(Sol)

리뷰는 구현과 다른 계열 모델이 맡는다. 실행은 공통 실행기 review-run.sh가 하고, 리뷰어 종류(opencode-sol · opencode-build · codex-cli)는 프로파일 값 하나로 고른다. 리뷰어가 무엇이든 요청 파일 형식·판정 규칙·회차 규칙은 같다.

  • 완료 근거는 done 파일 하나다. 실행기가 실제 종료 코드, RUN_ID, 리뷰 전후 snapshot(HEAD·작업 트리 식별자), 읽기 전용 여부를 기록한다. 로그 문자열이나 결과 파일 존재만으로는 완료도 통과도 아니다.
  • 결과 파일 첫 판정 줄은 # 판정: SHIP | BLOCK이고, 결과의 "검증 원장"에 요청한 HEAD가 그대로 있어야 한다. 다르면 이전 회차 인용으로 보고 unverified.
  • 조정자는 리뷰어의 원 판정과 별개로 실효 판정을 정한다(프로파일 block-on). 기본은 BLOCK만 막고 MAJOR는 백로그·후속 task로 회수한다. 데이터 손실·권한 우회·비가역 위험([안전] 태그)은 강등하지 않는다.
  • 리뷰가 도는 동안 조정자는 리포에 파일을 쓰지 않는다. snapshot이 흔들리기 때문이다.

1-5. 프로젝트 프로파일

프로젝트 루트의 .claude/autonomous-chain.md. frontmatter는 값(검증 명령, 병렬 상한, 커밋·push 정책, 리뷰어, 사다리 등), 본문 절은 훅 지점에 덧붙일 절차다. 없으면 기본값으로 동작한다. 자세한 사용법은 3절.

1-6. agent-orchestrator와 어댑터

worker를 터미널의 옆 pane으로 띄우거나 다음 세션을 새 탭에 여는 일은 터미널 오케스트레이션 툴(현재 herdr)에 의존한다. 스킬이 툴 명령을 직접 부르면 툴이 바뀔 때마다 규칙 문서를 고쳐야 하므로, 2.3.0부터 모든 호출을 agent-orchestrator <동작> 하나로 감췄다.

  • 동작: backend, whoami, tab-open, pane-open, self-name, agent-start, agent-send, agent-wait, agent-status, agent-session-id, agent-transcript, agent-read, agent-keys, pane-run, close, list. stdout은 값 한 줄, 사유·경고는 stderr, JSON 출력 없음.
  • 어댑터: 진입점이 인자를 검사한 뒤 adapters/<백엔드>.sh를 불러 op_<동작> 함수를 호출한다. 지원하지 않는 동작은 함수를 정의하지 않으면 된다(진입점이 10을 반환). 툴 특이사항은 docs/<backend>.md 한 곳에만 적는다. 새 툴을 붙일 때는 어댑터 파일·자동 판정 한 줄·설치물 목록·가짜 바이너리 시험을 추가한다.
  • 종료 코드가 스킬과의 계약이다. 특히 아래 세 값이 "옆 pane을 못 쓰면 내장 서브에이전트로 내려간다"를 가능하게 한다.

2. 로직 — 한 마일스톤이 도는 흐름

2-1. 전체 흐름

체인은 계획 세션에서 시작한다. 계획 세션은 목표와 기존 상태를 확인하고, 권한(로컬 커밋, push, 외부 시스템 쓰기, 새 비용, 상한 초과 사다리)을 한 번만 묻고 상태 파일 authority에 적는다. 이 스킬의 기본값, 리뷰 SHIP, 추천안 선택은 승인을 새로 만들지 않는다. 그다음 chain-planner-deep이 최초 계획을 쓰고, 리뷰 게이트가 계획을 검토한다. 이후 마일스톤 세션마다 아래 흐름이 반복된다.

중요한 운영 원칙 몇 가지:

  • 원인과 위치가 명확한 작은 수정은 worker를 띄우지 않는다. 리뷰가 원인 위치(파일:줄)와 재현 입력을 특정했으면 조정자가 직접 고치고, 재현 회귀 시험 1~2건과 바꾼 모듈의 영향 시험만 돌린다. 운영 실측에서 worker BLOCK 수정 1회가 31~96분이었고, 같은 성격의 국소 수정을 조정자가 했을 때 약 10분이었다.
  • 검증 예산: task 완료 때는 worker가 영향 시험만, 웨이브 통합 때 전체 검증 1회, 마감 때 전체 검증 1회. 수집 0건·skip·미실행은 통과가 아니며 총계를 함께 기록한다.
  • 사람 필요 항목은 묶어서 한 번만 알린다. 착수 때 로그인·자격증명·승인·시각 확인·기기 조작이 필요한 task를 한 목록으로 질문 대기열에 올리고 푸시 알림을 1회 보낸다. 그 항목에 의존하는 task는 웨이브 뒤쪽으로 보낸다. 운영 분석에서 사람 대기가 가장 큰 시간 항목이었기 때문이다.
  • 멈춤 조건이 아닌 선택지는 기다리지 않는다. 보고에 "추천안 x로 진행 중, 바꾸려면 말씀해 주세요"라고 쓰고 바로 진행한다.

2-2. worker 실행 3단계

2.3.0에서 worker·planner·리뷰를 어떤 수단으로 돌릴지 3단계 기준을 정했다. 판정 규칙(보고서·done 파일·snapshot·게이트)은 단계와 무관하다.

2-3. 게이트 회차와 조건부 마감

리뷰 게이트는 무게에 따라 회차가 다르다.

게이트대상무게회차
계획전체 계획마일스톤 2개 이상이면 무거움, 1개면 가벼움3회 / 1회
웨이브 통합그 웨이브의 고위험 task 변경 묶음(push 전)가벼움1회
마감(화면)화면만 바뀐 마일스톤리뷰 없음build · 스모크
마감(데이터)데이터·권한·스키마·이관이 들어간 마일스톤가벼움1회
마감(heavy)저장 스키마·이관 계약을 처음 확정하는 마일스톤, 출시 검토 마일스톤무거움3회
  • 가벼운 게이트: 리뷰 1회 → BLOCK 수정 → 영향 시험으로 조정자가 확인 → 재검토 없이 진행. 기록은 fixed-local <커밋> · <시험>.
  • 무거운 게이트: 최초 + 재검토 2회. 재검토는 delta 검토가 기본이고, 범위는 "직전 finding의 해소 여부 + 이번 수정이 만든 회귀"로 고정한다. 범위 밖 새 finding은 백로그로 받는다(재현된 안전 위험만 예외).
  • 부분 해소가 두 번 나오거나 같은 결함 계열이 두 번째 나오면, 반례를 하나씩 고치지 않고 계열의 공통 원인을 고치는 수정 하나로 바꾼다.
  • 상한 초과 사다리: 무거운 게이트가 3회 뒤에도 BLOCK이면 사용자에게 묻지 않고 기본 사다리 [extra-rounds:1, carry-reversible, stop]를 밟는다. ① 수정·재검토 1회 더 ② 남은 BLOCK이 모두 되돌릴 수 있는 제품 결함(UI·로컬 코드)이면 SHIP으로 기록하지 않고 carried로 다음 웨이브 task에 넘긴 뒤 조건부 마감 ③ 되돌리기 어려운 대상이 걸려 있으면 멈춤.

조건부 마감은 사용자 확인 없이 넘어갔다는 사실을 숨기지 않기 위한 장치다. 마감 보고와 인계 문서에 별도 절을 두고 한도에 닿은 게이트와 회차, 반영한 수정 커밋, 남은 finding, 되돌리는 비용, 이월한 task id를 적는다. 남은 finding은 다음 상위 게이트의 검토 범위에 들어간다.

구현 모드와 출시 검토

마일스톤은 기본적으로 구현 모드(build)로 돈다. 마감을 막는 BLOCK은 6가지로 좁힌다: 주 흐름 미동작, 기존 기능 회귀, 데이터 손실·권한·보안 오류, 크래시·빌드 실패, 되돌리기 어려운 대상, 사용자가 시각 확인에서 지적한 것. 그 밖의 경계 조건(화면 폭, 긴·빈 데이터, 접근성 세부, 시각 다듬기)은 백로그로 미룬다. 출시 품질 검사는 사용자가 "출시 검토해줘"처럼 명시 요청할 때만 harden 마일스톤을 넣어 한 번에 한다.

2-4. 실패 처리 사다리와 30분 상한

"원인 모를 실패"는 worker가 부분 완료·막힘으로 끝나거나 보고서가 없음, 고쳤는데 같은 증상이 남음, 원인 가설이 빗나감을 말한다. 오타·빠진 import 같은 명백한 실패, flaky 의심(1회 재실행), 환경 문제(index.lock·포트·오래된 빌드 산출물·API 재시도)는 세지 않는다.

  1. 원인 모를 실패 1번 → 조정자는 두 번째 직접 시도를 하지 않는다. 새 chain-worker-xhigh(Opus xhigh) 1개에 조사와 근본 수정을 함께 맡긴다. 지시서에는 재현 명령, 확인된 사실, 의심 지점(검증 대상으로 표시), 반박된 가설 전부, 금지(대기 늘리기·시험 완화·우회 같은 증상만 맞추는 수정)를 넣는다.
  2. xhigh도 실패 → 그 task만 blocked로 두고, 의존하지 않는 작업은 계속한다. 질문 대기열에 반박된 가설과 추천안을 올린다. 같은 방식으로 다시 돌리지 않는다.

프로파일 root-cause: sol이면 1단계 앞에 리뷰 모델의 읽기 전용 원인 조사 1회를 넣는다.

30분 상한(구현 모드만): 화면·배치·시험 하니스·간헐 실패·도구 같은 일반 문제는 한 문제에 30분이 넘으면 멈추고 백로그에 [30분]으로 적은 뒤 다음 task로 간다. 단독 재실행에서 통과하는 간헐 실패는 [quarantine]으로 올린다. 변환기·직렬화·저장 스키마·이관·권한 같은 데이터 등급 문제는 상한 없이 그 자리에서 해결한다.

2-5. 멈춤 조건

체인은 아래 경우에만 멈추고 보고한다. 시간 경과·침묵·timeout만으로는 멈추지 않으며, timeout이나 빈 응답은 성공도 실패도 아닌 unverified로 기록한다. 멈출 때는 진행 보드와 결정이 필요한 질문 id·추천안을 쓰고 푸시 알림을 1회 보낸다.

#멈춤 조건
1남은 작업이 모두 권한 대기나 사용자 결정 대기에 걸려 진행할 독립 작업이 없음
2같은 task가 재시도와 조정자의 직접 마무리 뒤에도 실패
3다음 마일스톤의 목표를 계획과 상태에서 찾을 수 없음
4프로파일 stop-conditions에 해당
5필수 리뷰 게이트(계획 검토, 마일스톤 최종 검토)를 재시도 뒤에도 실행할 수 없음
6무거운 게이트가 3회 뒤에도 BLOCK이고 사다리가 stop에 닿음 — 기본 사다리에서는 되돌리기 어려운 대상(스키마·배포/보안 설정·계약 문서·비가역 런타임 동작·외부 시스템 쓰기·main 병합)이 걸린 BLOCK일 때만

권한 밖 작업(정책 충돌, 새 비용, 외부 쓰기)은 체인 전체를 멈추지 않는다. 추천안을 대기열에 적고 그 작업만 실행하지 않는다.

2-6. 정지 감시

① 내장 서브에이전트는 완료 알림이 오므로 정지 감시가 필요 없다. ③ pane worker가 있는 웨이브에만 감시 스크립트를 띄운다. 2.2.0부터 판정 기준은 파일 수정 시각(mtime)이 아니라 transcript 내용(마지막 진척 시각, 그 뒤의 API 재시도 수)과 agent-status다. API 오류 재시도도 transcript를 갱신해서, mtime만 보던 시절 한 worker가 99분 동안 코드 변경 없이 돌았는데도 감지되지 않았다.

  • 출력 종류: 정지 후보(working인데 진척 10분 이상) · API 재시도 반복 · 권한·입력 대기 · 끝남 · 감시 불가(UNVERIFIED — mtime으로 대신 추정하지 않는다).
  • 이벤트는 후보일 뿐이다. 받으면 화면을 1회 보고, 재지시, 그래도 안 되면 재기동 순서로 처리한다. API 재시도는 환경 문제로 실패 횟수에 넣지 않는다.
  • 별도로 worker 보고서의 - 진행: 줄을 20초 간격으로 읽어 진행이 바뀔 때마다 한 줄 보고한다. 진행 이벤트가 30분 넘게 없으면 그 사실을 보고한다(멈춤은 아니다).

2-7. 세션 인계

비용은 컨텍스트 크기 × 남은 턴이라 세션이 길어질수록 커지고, 운영 실측에서 컨텍스트가 큰 조정자 세션에 실수가 몰렸다(인과는 확인되지 않음). 그래서 마일스톤마다 세션을 바꾼다. 조정자 컨텍스트가 150K 토큰을 넘으면(예시 수치) 마일스톤 도중이라도 안전한 지점에서 인계한다. 체인이 끝난 세션에서 새 체인을 시작하지 않는다.

ROOT=$(agent-orchestrator tab-open "[OC] <짧은 이름> M<n+1>")   # 새 탭, 포커스 이동 없음
agent-orchestrator agent-start <next> "$ROOT" --kind claude -- <현재 조정자와 같은 플래그>
agent-orchestrator agent-send <next> "<상태 파일>과 <인계 문서>를 읽고 auto-chain 스킬로 M<n+1>을 진행해. 부모 조정자 pane: <id>" --confirm
# stdout이 working 또는 done이면 인계 증거
  • 프롬프트는 줄바꿈 없는 한 줄이다(줄바꿈은 중간 제출로 해석된다). 문서가 진본이고 프롬프트는 포인터다.
  • 기동은 인계 시도당 1회. 응답을 잃으면 에이전트 목록에서 이름을 찾아 있으면 메시지만 다시 보낸다.
  • 부모 정리는 child가 한다. 이어받은 세션이 상태를 읽은 직후 부모 pane을 닫는다. 부모가 스스로 닫으면 실행 중인 명령이 끊길 수 있기 때문이다.
  • 진행 중인 worker가 남아 있으면 인계하지 않는다. 예외는 ③ pane으로 띄운 롤링 분해 planner뿐이며, 인계 문서에 pane·보고서 경로를 적고 child가 회수한다.
  • 오케스트레이션 툴 밖이면 자동 기동하지 않고 인계 문서와 다음 세션 시작 명령 한 줄을 사용자에게 준다.
  • 이어받은 세션의 첫 응답은 항상 진행 보드다.

3. 프로젝트 설정으로 단계에 작업 덧붙이기 — gira 사례

3-1. 스킬은 뼈대, 프로파일은 살

스킬은 어떤 프로젝트에서나 같은 절차(분해·병렬 실행·회수·검증·리뷰·마감·인계)를 정한다. 프로젝트마다 다른 것 — 검증 명령, 무엇이 고위험인지, 진행 원장 갱신, 사내 시스템 반영, 커밋 전 감사 — 은 스킬을 고치지 않고 프로파일에 쓴다. 프로파일 훅 절은 공통 동작 다음에 실행되고, 훅이 authority에 없는 작업(외부 쓰기 등)을 요구하면 실행하지 않고 질문 대기열에 올린다. 즉 프로파일은 승인을 새로 만들 수 없다.

3-2. 훅 지점

절실행 시점
on-milestone-start마일스톤 세션 착수, 인계·상태 확인 직후
on-task-donetask 보고서 확인·조정자 커밋·상태 갱신 직후
on-wave-integrated웨이브 통합 검증·고위험 검토 통과 후, push 전
on-milestone-close마감 검증·최종 리뷰 통과 후, wrap-up·인계 전
high-risk고위험 판정 기준 추가(기본: 인증·권한, 데이터 원자성, 외부 시스템 쓰기, 스키마·외부 계약)
stop-conditions공통 멈춤 조건에 더할 프로젝트 조건

가장 작은 프로파일은 이 정도다.

---
chain-profile: 1
verify:
  full: "npm test && npm run typecheck"
commit: task
push: none
---

## high-risk
- `migrations/**` 변경

3-3. gira 프로파일 해부

gira는 사내 업무 시스템을 다시 만드는 프로젝트로, 한 리포 안에 두 시스템(업무 관리 시스템과 위키)이 있다. 두 시스템은 각자의 작업 트리(본 트리와 worktree)에서 진행되지만 프로파일 파일 하나를 공유한다. 이 프로파일이 공통 뼈대 위에 무엇을 얹는지 순서대로 본다. 아래 인용은 구조를 보이기 위해 짧게 줄이고 값을 일반화한 것이다.

① frontmatter — 값

---
chain-profile: 1
verify:
  full: "<프로젝트 CLI> test < /dev/null"
  static: "<프로젝트 CLI> verify static < /dev/null"
parallel-max: 2
commit: task        # task마다 조정자 커밋
push: wave          # 웨이브 통합 때 push
daily-log: wave
task-brief: docs/chain/_profile/task-brief.md   # worker 덧붙임 지시서
---

commit·push에는 스킬 기본값이 없다. 프로파일에 있으면 사용자가 그 프로젝트에 미리 둔 상시 정책으로 보고 계획 세션에서 다시 묻지 않는다. 값마다 근거(예: "겹치지 않으면 2개까지")를 본문에 한 줄씩 적어 둔다.

② 시스템 판별 — 모든 훅보다 먼저

조건시스템절차 문서체인 id 접두사
작업 트리가 위키 worktree이거나 브랜치가 위키 브랜치위키docs/chain/_profile/giki.mdgiki-
그 밖(본 트리, main)업무 시스템docs/chain/_profile/gira.mdgira-

판별 결과는 상태 파일 "## 결정"에 남기고, 상태 파일의 체인 id 접두사와 판별이 다르면 멈춘다. 한 체인은 한 시스템만 다룬다. 이렇게 하면 훅 절 본문은 "판별한 시스템의 절차 문서에서 같은 이름의 절을 수행한다" 한 줄로 끝나고, 시스템별 분기는 프로파일 본문에 늘어나지 않는다.

③ 권한 — authority와 외부 쓰기 범위

계획 세션은 권한을 한 번 묻는다. gira 프로파일은 외부 쓰기를 물을 때 쓸 정확한 문구를 체인 종류별로 미리 적어 둔다.

  • 업무 시스템 재구축 마일스톤 체인: "사내 이슈 트래커의 착수·task 완료·마감 반영과 완료 전환, 허용된 범위만"
  • 그 밖의 phase(로컬 검토 등): no — 회사 반영 대상이 아님
  • 위키 체인: "위키 동기화 도구 apply — 허용된 이슈 칸과 허용된 위키 페이지 2개의 허용 칸만"

훅 절차 안의 [외부쓰기] 단계는 상태 파일 authority.external-write에 이 범위가 있을 때만 실행된다. 실제 진행 중인 체인의 상태 파일 frontmatter는 이런 모양이다.

authority: { local-commit: yes, push: wave, external-write: no, new-cost: no,
             escalation: [extra-rounds:1, carry-reversible, stop] }
verify-full: "<프로젝트 CLI> test < /dev/null"
skill: auto-chain 2.3.0
reviewer: opencode-sol
backend: herdr <조정자 pane>

④ 조정자 커밋 규칙 — 스킬 커밋 절차에 덧붙임

  1. 보고서의 변경 파일과 보고서 파일만 경로 지정 스테이징
  2. 스테이징된 이름 목록이 그 목록과 같은지 확인. 다르면 커밋하지 않음
  3. 커밋 위생 감사 도구 실행. 적발이 1건 이상이면 커밋하지 않고 원인 task에 수정 worker를 보냄
  4. 경로 지정 커밋. 메시지 형식은 시스템별(feat(<영역>): <요약>(<task-id>) 등)

여기에 "원장·대시보드·회사 반영 기록 커밋은 구현 커밋과 따로 한다"는 규칙이 붙는다. 자기 커밋 해시를 원장에 다시 쓰는 순환을 막기 위해서다. 작업 트리에 원래 있던 미커밋 파일은 건드리지 않는다.

⑤ 훅 절 → 시스템별 절차 문서

업무 시스템 절차 문서는 진행 관리 프로젝트 스킬을 진본으로 두고, auto-chain의 각 시점에 어떤 명령을 어떤 순서로 돌릴지만 정한다.

훅gira가 덧붙이는 일(요약)
on-milestone-start진행 원장 점검(읽기 전용) → 다른 세션이 같은 마일스톤을 진행 중인지 확인(원장 미커밋 변경이면 멈춤) → 사내 시스템 상태 읽기 대조 → 첫 task 착수를 원장에 기록하고 원장만 커밋 → [외부쓰기] 이슈 시작일이 비어 있을 때만 착수 반영
on-task-donetask 커밋 해시와 보고서의 "실행한 시험"을 증거로 원장 갱신(시험 증거는 다시 실행 가능한 단일 명령이어야 함) → 원장만 따로 커밋 → [외부쓰기] task 완료 반영(실패는 "회사 반영 미완료"로 기록하고 제품 done은 되돌리지 않음) → 결정 제안을 결정 기록에 추가
on-wave-integrated공통 verify 뒤 라우트·생성 계약을 바꾼 웨이브면 offline 검증 추가 → 검증 중 원장 커밋 금지 → 밀린 반영 따라잡기 → 일지 누적
on-milestone-close종료 조건마다 원장에 충족 기록 → 마감 전체 게이트(두 Python 버전 시험, offline 검증, 저장소를 바꿨으면 DB 통합 시험) 백그라운드 실행 → 마감 확인서 생성·유효성 확인(이후 원장 변경 금지) → [외부쓰기] 최종 진척률·완료일 반영과 완료 전환 → 인계 문서는 지우지 않고 새로 작성

위키 쪽 절차 문서(giki.md)는 같은 훅 이름으로 위키 고유의 시험·동기화 단계를 정한다. 오래 걸리는 명령은 모두 백그라운드로 실행하고 완료 알림을 받는다는 공통 규칙도 프로파일이 적는다.

⑥ high-risk와 stop-conditions

high-risk는 공통 기본에 경로 단위로 더한다. 예: 인증·세션·권한 모듈, 저장소 원자성·발번·SQL·트랜잭션 어댑터, 회사 동기화·진행 도구, 위키 권한·가시성, 저장 경합·DDL, 외부 파일 파싱(zip·XML·JSON) 이관 코드, 데이터 삭제 경로. 이 경로를 건드리는 task는 웨이브 통합 때 리뷰 게이트 대상이 된다. 반대로 여러 task가 함께 고치는 공유 결선 파일(라우트 정책·도구 카탈로그 등)은 고위험이 아니라 조정자 소유로 두고 조정자가 한 커밋으로 묶는다.

stop-conditions는 공통 6개에 9개를 더한다. 요지는 "회사 시스템과 사람 판단이 걸린 것은 멈춘다"이다.

  • 시스템 판별과 체인 id 접두사가 다름
  • 같은 시스템을 다른 세션이 진행 중인 징후(원장·회사 반영 owner는 하나)
  • 운영 반영·데이터 삭제·컷오버·배포가 필요함
  • 승인 범위 밖 회사 쓰기(상태 역전환, 부모 이슈, 진척률 감소, 기존 다른 날짜 수정, 허용 페이지 밖 쓰기 등)
  • 회사 반영이 실패했거나 전송 상태가 확정되지 않음 — 다시 보내거나 새 실행으로 우회하지 않음
  • 회사 시스템 인증이 없거나 401·403 — 토큰을 채팅에 요구하거나 출력하지 않음
  • 회사 원문·PII·비공개 원자료를 커밋·일지·콘솔에 남겨야 하는 상황
  • 사람 판단이 필요한 충돌 해소 명령 — 그 task·단계만 보류하고 독립 작업은 계속
  • 철회된 쓰기 허가의 재발급이 필요함

정리하면: 스킬은 "task가 끝나면 보고서를 확인하고 커밋한 뒤 상태를 갱신한다"까지만 안다. 그 다음에 진행 원장을 갱신하고, 원장을 따로 커밋하고, 권한이 있을 때만 사내 이슈 트래커에 반영하고, 실패하면 무엇을 하지 말아야 하는지는 gira 프로파일과 절차 문서가 정한다. 같은 스킬이 다른 프로젝트에서는 verify.full 한 줄짜리 프로파일로도 그대로 돈다.

4. 용어집

조정자
마일스톤 하나를 맡는 메인 세션(오케스트레이터). worker 기동·회수, 커밋, 상태 파일·질문 대기열 기록, 통합 검증을 한다. git index 쓰기는 조정자만 한다.
마일스톤
세션 하나가 조정하는 작업 단위. 모드(build/harden), 등급(화면/데이터), 마감 게이트 무게를 가진다.
웨이브
소유 파일이 겹치지 않아 동시에 돌릴 수 있는 task 묶음. 끝나면 통합 검증을 1회 한다.
task
worker 하나가 구현하는 단위. 인수 기준·소유 파일·등급·고위험 여부가 계획에 표시된다.
worker
task를 구현하는 Claude 에이전트. stage·commit·push를 하지 않고 보고서를 쓴 뒤 한 줄을 반환한다.
게이트
리뷰 모델(Sol)이 판정하는 검토 지점. 계획·웨이브 고위험·마일스톤 마감. 무거운 게이트 3회, 가벼운 게이트 1회.
delta 검토
재검토 방식. 직전 finding의 해소 여부와 이번 수정이 만든 회귀만 본다.
실효 판정
리뷰어의 원 판정에서 심각도 매핑(block-on)과 범위 규칙을 적용해 조정자가 정한 최종 판정.
사다리
상한 초과 사다리(escalation). 무거운 게이트가 3회 뒤에도 BLOCK일 때 밟는 칸 목록. 기본 [extra-rounds:1, carry-reversible, stop].
조건부 마감
되돌릴 수 있는 결함을 다음 웨이브로 넘기고 닫은 마일스톤. SHIP으로 기록하지 않고 별도 절로 보고한다.
결함 계열
근본 원인 패턴이 같은 BLOCK 묶음. "올바른 모양"을 이후 worker 지시서와 리뷰 요청에 넣어 재발을 줄인다.
백로그
구현 모드에서 마감을 막지 않고 미룬 경계 조건 결함, [30분]·[quarantine] 항목의 원장.
프로파일
프로젝트 루트 .claude/autonomous-chain.md. 값(frontmatter)과 훅 절(본문)로 스킬 위에 프로젝트 절차를 얹는다.
훅 절
프로파일의 on-milestone-start 등. 해당 시점의 공통 동작 다음에 실행된다.
authority
계획 세션에서 한 번 받은 권한(로컬 커밋, push, 외부 쓰기, 새 비용, 사다리). 스킬 기본값·리뷰 SHIP·프로파일은 이를 새로 만들지 않는다.
done 파일
headless 실행기가 쓰는 완료 기록. 실제 종료 코드, RUN_ID, 전후 snapshot, 읽기 전용 여부를 담는다. 리뷰 완료의 유일한 근거다.
snapshot
검증·리뷰 대상 상태의 식별자(HEAD와 작업 트리 식별자, 대상 파일 해시). 요청과 결과가 같아야 판정을 읽는다.
인계
상태 파일과 인계 문서를 남기고 새 탭에 다음 조정자 세션을 기동하는 일. 부모 pane은 child가 닫는다.
롤링 분해
최초 계획 뒤 마일스톤 task를 한 마일스톤 앞서 분해하는 방식. Mn의 마지막 웨이브 기동 직후 Mn+2를 분해한다.
agent-orchestrator
터미널 오케스트레이션 툴을 감추는 명령. 동작 이름과 종료 코드가 계약이고, 툴별 차이는 어댑터가 맡는다.
진행 보드
10줄 이내 고정 형식의 진행 요약. 마일스톤 착수, 웨이브 통합, 게이트 판정, 멈춤, 인계 직전에 낸다.
