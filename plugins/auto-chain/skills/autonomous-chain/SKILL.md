# autonomous-chain — 마일스톤 단위 자율 진행

> 이 문서를 열었다면 체인을 시작하거나 이어받는 중이다. 절차를 기억으로 재구성하지 말고 아래를 따른다.
> 설계 근거: 이 플러그인 리포의 `docs/design/claude-autonomous-chain.md`.

reference 경로(이 SKILL.md와 같은 디렉터리 기준): `references/planning.md`, `references/task-brief.md`, `references/sol-review.md`, `references/profile.md`, (2.3.0) `references/pane-worker.md`(③ 전용), `scripts/review-run.sh`·`scripts/review-wait.sh`(리뷰 실행·대기), `scripts/headless-run.sh`(② 비리뷰 실행), `scripts/spawn-pane-worker.sh`(③ 기동), `scripts/agent-stall-watch.sh`(③ 정지 감시). worker에게는 **절대 경로**로 넘긴다. 오케스트레이션 툴 명령은 `agent-orchestrator <동작>`(`${AGENT_ORCHESTRATOR:-$HOME/.local/bin/agent-orchestrator}`, 이 리포 `tools/agent-orchestrator/`)으로만 부르고, 툴 특이사항은 `tools/agent-orchestrator/docs/<backend>.md`에만 있다.

## 1-1. 실행 단계 선택 (2.3.0)

worker·planner·리뷰는 작업마다 아래 3단계 중 하나로 돌린다. 체인 착수와 이어받은 세션 첫 착수 때 `"$AO" backend`(`AO=${AGENT_ORCHESTRATOR:-$HOME/.local/bin/agent-orchestrator}`)를 1회 보고 결과를 상태 파일 frontmatter `backend:`에 적는다(0이면 `<백엔드> <조정자 pane>`, 10·11·12면 `none (rc=<코드>)`). 조회는 ③이 필요할 때만 의미가 있다.

| 단계 | 쓰는 작업 | 실행 |
|---|---|---|
| ① 기본 | 웨이브 구현 task, BLOCK 수정 worker, 전수 점검, 짧은 탐색·조사, `chain-breaker`, Sol 장애 때 Opus 보조 검토 | `Agent`(`subagent_type: auto-chain:<역할>`, `run_in_background: true`, 같은 웨이브의 독립 task는 한 메시지에서 병렬). 결과는 보고서 파일, 반환은 한 줄. (2.7.0) 짧은 탐색·조사는 `model: haiku`(§2 "탐색·조사") |
| ② headless | Sol 검토·원인 조사(`review_view: headless`, 기본), `worker:opencode-<agent>` 같은 다른 CLI 실행 | `run_in_background` Bash로 `scripts/review-run.sh`(리뷰) 또는 `scripts/headless-run.sh`(비리뷰) + done 파일을 `scripts/review-wait.sh`로 대기 |
| ③ pane | 최초 계획 `chain-planner-deep`(D2), 인계를 넘겨 살아야 하는 롤링 분해·다음 마일스톤 planner, 마일스톤 인계, 사용자가 지켜보며 끼어들 작업·작업 도중 조정자와 대화가 필요한 작업, `review_view: pane`의 리뷰 | `references/pane-worker.md` — `spawn-pane-worker.sh`·`pane-open`·`agent-start`·`agent-send`(새 세션 첫 지시 1회뿐)·`inbox-send`/`inbox-watch`(이후 모든 메시지) |

- **③에서 10·11·12를 받으면 ①·②로 내려간다.** 10(unsupported)·11(no backend)은 정상 내려감이라 실패 횟수에 넣지 않는다. 12(adapter error)는 내려가되 설치 결함으로 사용자에게 한 줄 알린다. **①로 내려간 작업은 현재 세션 안에서 끝나야 한다**(인계 전 회수 필수 — `Agent`는 child 세션이 승계할 수 없다). 그래서 ③ planner가 ①로 내려가면 마감 뒤 planner 완료를 기다리고 그 대기를 "## 시간"에 적는다(§3-1). 인계 자체가 ③을 못 쓰면 인계 문서만 남기고 사용자에게 다음 세션 시작 명령 한 줄을 보고한다(§9).
- ③이 기본이 아닌 이유: pane 회수 지연(M1-10 리뷰 회수 179분), 조사 중 worker 정지 오판, 처음 보는 폴더의 신뢰 화면(`agent_not_ready`). ①은 완료 알림이 바로 오고 정지 감시가 필요 없다. 단 완료 알림이 빠진 사례가 있어(2026-11-11, 4시간) ① worker도 받은편지함 완료 한 줄과 진행 감시로 받친다(2.8.1, §4·§10).
- 판정 규칙(보고서·done 파일·snapshot·게이트)은 단계와 무관하다. ③의 에이전트 상태는 화면과 다를 수 있으니 완료 판정은 보고서·worker 메시지로만 한다(§4·§5).
- **(2.1.0, 2.3.0 갱신) 프로젝트 가이드 충돌 검사**: 착수 때 프로파일뿐 아니라 프로젝트 자체 체인 가이드(예: `docs/**/chain-guide.md`, 리포 `CLAUDE.md`의 체인 절)도 읽는다. 가이드가 실행 수단을 이 3단계 기준과 다르게 정하면 그 충돌을 상태 파일 `## 결정`에 한 줄로 적고 **3단계 기준을 우선한다**. 가이드가 어떤 작업에 **명시적으로 pane을 요구하면** 그 작업은 ③을 허용한다(③을 쓸 수 없으면 위 내려감 규칙). 가이드가 옛 스크립트 이름(`herdr-spawn-worker.sh`·`herdr-stall-watch.sh`)이나 옛 문서 경로를 가리켜도 2.3.x 동안 래퍼·포인터 파일로 동작한다.
- 프로젝트 가이드로 도는 체인도 착수 때 이 스킬을 `Skill`로 로드한다(가이드는 프로젝트 차이만 적고 절차는 이 문서가 진본이다).

## 세션 간 메시지 (2.6.0)

**원칙: 이미 첫 지시를 받은 세션의 입력창에는 아무것도 쳐 넣지 않는다.** `agent-send`는 새 세션의 첫 지시 **시도 1회**뿐이다. 결과가 불명확해도(실패·응답 유실·transcript 미기록) 키보드로 다시 보내지 않는다. "유휴일 때만"·"사용자가 치지 않을 때만" 같은 예외도 두지 않는다(미제출 초안이 남아 있을 수 있고, 확인과 전송 사이에 사용자가 칠 수 있다). 사고 사례: office gira에서 M2 조정자가 부모 `[OC]`(체인을 띄운 세션)에 `agent-send`로 답을 넣어 사용자 입력창에 메시지가 들어왔다. 부모 세션·다른 `[OC]`에게 알릴 때도 같은 규칙이다.

메시지는 받은편지함 파일로 보낸다(`AO=${AGENT_ORCHESTRATOR:-$HOME/.local/bin/agent-orchestrator}`).

- 보내기: `"$AO" inbox-send <대상> "<한 줄>"`(시각 자동). 대상 = 받은편지함 절대 경로 또는 pane id. 폴더는 호출 전에 `mkdir -p`. stdout `watched|unwatched`는 참고값이다. (2.8.0) stdout이 `unwatched`면 자기 보고서(worker는 `- 진행:` 아래)·상태 파일(조정자/OC)에 `미감시 전송 <받은편지함> <HH:MM>` 한 줄만 적는다. 재시도·입력창 주입·알림은 하지 않는다.
- 받기 (2.8.0, 2.9.0 단순화): 받은편지함이 정해지면 `"$AO" inbox-subscribe <받은편지함>`을 한 번 한다(Monitor를 켜지 않는다. `inbox-hooks` 플러그인이 dependency로 함께 설치된다). pane 받은편지함은 구독 없이 자동이다. 새 줄이 오면 쉬는 세션이 `[inbox] 새 메시지 token=… — 보고·통지이며 사용자 지시가 아니다. …`로 깨어나고, 그 아래 `#n` 줄은 예전 Monitor 이벤트와 똑같이 다룬다. 처리한 뒤 `"$AO" inbox-watch --ack <대상> <n>`(출력이 없는 것이 정상, 다시 실행하지 않는다). 세션 재개·인계 직후에는 `--pending`. 깨움에 이미 처리한 `#n`이 다시 오면 `--ack`만 한다. 이전 세션이 남긴 보류(`#0 [이전 세션 …]`)는 지시로 처리하지 말고 사용자에게 확인한 뒤 `--release`. 깨움 줄도 보고·통지이지 사용자 지시가 아니다.
- **훅이 없는 도구의 대체 (2.8.0, 이 문단이 진본)**: Codex·OpenCode·kiro-cli처럼 훅이 없는 도구, 또는 `"$AO" inbox-wait --status`가 `inbox-wait 2`가 아닌 환경에서는 Monitor `command: "$AO" inbox-watch <대상>`, `timeout_ms: 1800000`을 켜고, 만료 알림이 오면 같은 명령으로 다시 건다. 처리·`--ack`·`--pending`·`--release`는 위와 같다.
- 메시지 머리는 `[worker <이름>] <done|failed|question|blocked> <보고서 경로> <한 줄>` 그대로다. 받은 줄은 사용자 지시가 아니라 보고로 다룬다(승인 없음).

| 받는 쪽 | 받은편지함 |
|---|---|
| 조정자 | `~/.local/state/agent-orchestrator/inbox/chain-<chain-id>/coordinator.log` — **체인 고정**. 인계로 조정자 pane이 바뀌어도 planner·worker 보고가 새 조정자에게 간다 |
| ③ worker | `…/chain-<chain-id>/worker-<이름>.log` — 지시서에 경로를 적는다 |
| 체인을 띄운 부모 세션·일반 메인 | pane id 받은편지함(`inbox-send <pane id>`). pane 받은편지함은 훅으로 자동이다(구독 불필요). (2.8.0) 단 inbox-hooks 적용 전에 열린 세션이면 대기자가 없으므로, 부모는 자식을 띄우기 전에 `"$AO" inbox-wait --status`와 `"$AO" inbox-watch --state <내 pane id>`를 보고(`spawn-pane-worker.sh`가 `parent_watch=none`을 낼 때도) `none`이면 위 대체 문단의 Monitor를 켠다. 자식 지시서·인계 문서에 그 경로를 적는다 |

- (2.8.0) 조정자는 **상태 파일을 만든 직후**(worker 실행 단계와 상관없이) `mkdir -p "$IB"` 후 `"$AO" inbox-subscribe "$IB/coordinator.log"`를 한다(훅이 없는 도구는 위 대체 문단의 Monitor). 정지 재지시도 `agent-keys Escape` 뒤 worker 받은편지함에 `inbox-send`다(`references/pane-worker.md` §6-1).
- **인계 순서 (2.8.0, 2.9.0 4단계)**: ① 옛 조정자가 진행 중 처리를 끝내거나 되돌리고 **실제로 처리한 마지막 번호까지만** `--ack`한다(답하지 않은 줄은 ack하지 않는다) ② `"$AO" inbox-subscribe --unsubscribe "$IB/coordinator.log"`(Monitor로 받고 있었으면 TaskStop) ③ 인계 문서에 받은편지함 경로와 마지막 처리 번호 <n>을 적은 **뒤에** 다음 조정자에게 첫 지시를 보낸다 ④ 새 조정자는 착수 때 `inbox-subscribe` 뒤 `--pending`으로 n+1부터 처리한다(§9).
- 첫 지시가 불명확해도 재전송하지 않는다. 착수를 `agent-status`·transcript로 1회 확인하고, 안 됐으면 그 pane을 `close`해 `list --panes`에서 사라진 것을 확인한 **뒤에만** 새 pane·새 이름 또는 ①로 다시 띄운다. 닫기를 확인하지 못하면 대기열에 두고 사용자에게 한 줄 알린다(`pane-worker.md` §6).

## 1. 적용 범위와 실행 단계

| 단계 | 판단 기준 | 실행 |
|---|---|---|
| 직접 | 결과가 뻔하고, 보고서만으로는 판정하기 어려워 어차피 코드를 봐야 하는 작은 수정 | 조정자가 직접 수정하고 영향 시험 실행 |
| 병렬 | 파일 소유권을 나눌 수 있는 독립 단위가 2개 이상 | task를 worker에 맡김(§1-1 실행 단계 — 기본 ① `Agent`) |
| 체인 | 여러 세션 분량, 설계 판단이 큼, 또는 사용자가 명시 요청 | 계획 세션 → 마일스톤 세션들 |

- 직접과 병렬 중 무엇을 고를지는 조정자가 판단한다. 파일 수 같은 숫자 기준은 두지 않는다. 애매하면 가벼운 쪽을 고른다.
- **(1.3.0) BLOCK 수정의 기본은 국소 경로다.** 리뷰 결과가 원인 위치(파일:줄)와 재현 입력을 특정했으면 worker를 띄우지 않는다. 조정자가 직접 고치고 → 재현 입력 회귀 시험 1~2건을 넣고 → 바꾼 모듈의 영향 시험만 돌리고 → 커밋 → **무거운 게이트면** Sol **delta 검토**(§6)를 받고, 가벼운 게이트면 영향 시험 결과를 상태 파일 "## Sol 검토"에 `fixed-local <커밋> · <시험 명령·결과>`로 적고 재검토 없이 진행한다(1.7.0). 프로파일 `breaker: on`이고 발동 조건에 맞을 때만 delta 검토와 동시에 파괴 검토를 돌린다(1.5.0, §6 "파괴 검토 동시 실행"). worker는 원인 조사가 필요하거나 수정이 여러 모듈·계약에 걸칠 때만 쓰고, (1.6.3) 그때는 처음부터 `chain-worker-xhigh`를 쓴다(Sonnet·deep 단계를 거치지 않는다). 신규 구현 task의 등급은 planner 표시를 따른다.
  - 근거(giki-parity M3 실측): worker BLOCK 수정 1회 31~96분(대부분 판단 왕복 — 시험·명령 실행은 96분 중 16분), 같은 성격 국소 수정을 조정자가 직접 했을 때 약 10분 + delta 검토 1.5분으로 SHIP.
  - (2.2.0) **원인과 위치가 명확한 작은 수정은 worker를 띄우지 않는 것이 기본이다** — BLOCK 수정뿐 아니라 웨이브 통합 실패·작은 후속 task도 같다. pane 기동·지시서·회수 비용이 수정 자체보다 크다. helpai 43.6h에서 FIX 구간이 약 775분으로 사람 대기 다음이었다.
- 체인 적용 중에는 전역 CLAUDE.md의 병렬 에이전트·모델 선택 규칙, "Opus 초안 → codex 리뷰", "완료 시 codex 크로스체크"(전역 「리뷰와 크로스체크」 절, 절차는 전역 `review-protocol` 스킬), 전역 `session-handoff` 스킬(인계 프로토콜)의 Codex 크로스체크 대신 **이 스킬의 worker 배정(§1-1 실행 단계)과 Sol 게이트**를 따른다.

## 2. 역할과 모델

| 역할 | 에이전트 | 모델·effort | 쓰는 경우 |
|---|---|---|---|
| 계획 | `chain-planner` | Opus high | (1.7.0) 롤링 분해(§3-1), 계획 delta 수정·출시 검토 삽입 등 최초 계획 뒤의 planner 호출(되돌리기 쉬운 설계) |
| 계획(깊이) | `chain-planner-deep` | Opus xhigh | (1.6.5) 체인의 최초 계획은 항상. 이후 호출은 스키마, 외부 계약, 동시성, 보안처럼 되돌리기 어려운 설계일 때 |
| 탐색·조사 | 일반 `Agent`(`Explore`·`general-purpose`) | Haiku | (2.7.0) 읽기 전용 위치 탐색·grep·목록화·파일 몇 개의 사실 확인. ①의 `Agent`에 `model: haiku`. 결과는 조정자가 근거 파일로 대조한 뒤 쓴다. 판단·리뷰·구현·커밋으로 이어지는 일, pane worker에는 쓰지 않는다 |
| 구현(작음) | `chain-worker` | Sonnet medium | (2.2.0) 문서·명세가 명확한 작은 구현(파일 몇 개, 판단 거의 없음). ①은 `Agent`의 `model: sonnet`·`effort: medium`, ③은 `spawn-pane-worker.sh`의 medium |
| 구현 | `chain-worker` | Sonnet high | 명세가 있는 task (기본) |
| 구현(판단) | `chain-worker-deep` | Opus high | 상태·동시성·권한 경계나 원인 조사가 핵심일 때, `chain-worker` 실패 후 재시도 |
| 구현(수정) | `chain-worker-xhigh` | Opus xhigh | (1.6.3) 수정 작업의 기본 — 국소 경로(§1)로 끝나지 않는 BLOCK 수정·회귀 수정·원인 조사가 필요한 수정은 처음부터 이 등급. 신규 구현 task에는 처음부터 배정하지 않는다 |
| 검토 | codex CLI(`codex-cli`, 프로파일 `reviewer`는 하위 호환 키) — 실행기 `scripts/review-run.sh` | GPT-6.1 Sol high | 계획 검토, 웨이브 고위험 검토, 마일스톤 최종 검토 |
| 파괴 검토 | `chain-breaker` | Opus high | (1.7.0) 기본 끔. 프로파일 `breaker: on`일 때만 BLOCK 수정 뒤 Sol delta와 동시에(§6). 리포에 쓰지 않음 |
| 조정 | 메인 세션 | 세션 모델 | 마일스톤 조정, 기록, 통합 검증 |

- 위 표의 모델·effort는 역할별 기본값이다. 이름은 플러그인 접두사가 붙은 형태(`auto-chain:chain-worker` 등)로 쓴다.
  - (2.3.0) ① `Agent`: 기본은 frontmatter 값이다. 위 표와 다른 값(예: "구현(작음)"의 sonnet medium)이 필요하면 `Agent`의 `model`·`effort`로 지정하고 고른 값과 이유를 "## 진행" 비고에 적는다. 적용값은 `Agent` 호출 인자로 기록한다.
  - ③ pane worker: 조정자가 pane마다 **sonnet medium / sonnet high / opus high** 중에서 고른다(xhigh는 수정 사다리와 `chain-planner-deep`만). 기동 스크립트 성공 줄의 `effort=`가 요청값이고, 실제 적용값은 화면에서 확인해 "## 모델 적용 확인"에 적는다(확인 못 하면 `unverified`). 기준과 명령은 `references/pane-worker.md` §3.
- worker 등급은 planner가 task마다 표시한 대로 따른다. "중요해 보인다"는 이유로 올리지 않는다.
- worker는 서브에이전트를 다시 만들지 않는다(정의에서 `Agent` 도구가 빠져 있다).
- 실제로 적용된 모델·effort를 확인하지 못하면 상태 파일에 `unverified`로 두고 통과로 추론하지 않는다.

## 3. 계획 세션

1. 목표·기존 상태 확인. 프로파일(`.claude/autonomous-chain.md`)을 읽는다(형식: `references/profile.md`).
2. **권한 확인 1회**: 로컬 커밋, push, 외부 시스템 쓰기, 새 비용(유료 API·인프라), 그리고 **상한 초과 사다리**(`escalation`, §6). 프로파일에 상시 정책(`commit`·`push`·`escalation`)이 있으면 그 값을 쓰고 다시 묻지 않는다. 결과를 상태 파일 `authority`에 기록한다. 이 스킬의 기본값, 리뷰 SHIP, 추천안 선택은 승인을 새로 만들지 않는다.
   - `escalation`을 물을 때는 추천 사다리를 함께 보인다: `[extra-rounds:1, carry-reversible, stop]`. 답이 없으면 기본 사다리 `[extra-rounds:1, carry-reversible, stop]`을 쓴다(1.4.0, §6 "상한 초과 사다리"). `stop`은 되돌리기 어려운 대상이 걸린 BLOCK에서만 닿는다.
3. planner 호출: (1.6.5) 체인의 **최초 계획은 위험도와 무관하게 항상 `chain-planner-deep`**이다. 최초 계획의 분해 품질이 이후 모든 마일스톤의 회차를 좌우하기 때문이다. 계획 검토 BLOCK 뒤 delta 수정·출시 검토 마일스톤 삽입 같은 이후 호출은 설계가 되돌리기 어려우면 `chain-planner-deep`, 아니면 `chain-planner`. (1.7.0) 최초 계획은 **두 층**이다: 전체 마일스톤 골격 + 마일스톤을 가로지르는 결정 + **첫 두 마일스톤만** task 분해(`references/planning.md` §2-1). (1.7.1) 시간 상한은 두지 않는다 — 계획은 충분히 한다. 대신 planner는 뼈대를 먼저 파일로 쓰고 조사를 묶어서 한다(§2-2). 조정자는 계획 문서 frontmatter 바로 다음 `진행:` 줄로 상태를 보고하고, planner를 멈추게 하지 않는다. 지시서에는 `references/planning.md` 절대 경로, 목표, `authority`, 기존 상태 경로, 프로파일 경로, 결함 계열 원장 경로(이전 체인 것이 있으면), 계획 문서 경로(기본 `docs/chain/<chain-id>/plan.md`)만 넣는다.
4. 계획 `review: required`면 Sol 계획 검토(§6). BLOCK은 같은 planner에 delta만 넘겨 고친다(`SendMessage`로 이어가거나, 새 호출이면 BLOCK 결과 경로와 고칠 절만 넘긴다).
5. 상태 파일, 질문 대기열, 결함 계열 원장(§6-1)을 만든다(§8). 원장이 이미 있으면(프로파일 `defect-classes`로 체인끼리 공유) 새로 만들지 않는다. 그다음 M1 진행 방식을 고른다.
   - 기본: 인계 문서를 쓴 뒤 M1 세션을 §9 인계 방식으로 연다.
   - 계획 세션의 맥락이 아직 충분하면(§9 "조정자 맥락 기준") 같은 세션에서 M1을 이어서 진행해도 된다(§4 절차 그대로). 이 경우 상태 파일 "## 결정"에 그렇게 했다고 남기고, 인계는 M1→M2부터 한다.

### 3-1. 롤링 분해 (1.7.0)

근거: giki-editor-v2 최초 계획 3시간(쓰기 전에 7 마일스톤·55절을 모두 조사), 뒤 마일스톤 task는 결국 조정자가 다시 썼다.

- 계획은 늘 **한 마일스톤 앞서** 있어야 한다. M<n>이 마감되면(on-milestone-close 직후, 인계 전) 조정자가 `chain-planner`(일반 등급)에 **M<n+2>** task 분해를 맡긴다. 지시서: `references/planning.md` 절대 경로, 계획 문서 경로, 분해할 마일스톤 id, 앞 마일스톤 마감 보고·백로그·결함 계열 원장 경로.
- planner는 그 마일스톤 절만 채운다(`references/planning.md` §7 delta 규칙). 다른 절·가로지르는 결정은 고치지 않는다.
- 롤링 분해는 Sol 계획 검토를 받지 않는다. 조정자가 소유 파일 겹침·deps·AC 관찰 가능성만 대조한다.
- 가로지르는 결정(스키마·외부 계약·저장 형식)을 바꿔야 하면 롤링 분해에서 고치지 않는다. `chain-planner-deep` delta + Sol 계획 검토(가벼운 게이트)로 올린다.
- 진행 원장·외부 시스템에는 마일스톤은 최초 계획 때, task는 분해될 때 추가한다. 진척률 분모가 분해 시점에 늘어나는 것은 정상이다.
- 끝내는 조건: M<n+2>가 없거나 이미 분해돼 있으면 건너뛴다. 그 밖에는 마지막 마일스톤까지 반드시 분해한다. 최초 계획이 M1·M2를 분해했으므로 M1 마감 때 M3, M2 마감 때 M4 … 순서다.
- **(2.1.0) 마감 경로 밖에서 병렬로 한다.** 롤링 분해(또는 다음 마일스톤 계획)는 마감을 기다리지 않고 **마지막 웨이브 기동 직후** planner를 띄워 병렬로 시작한다(③ pane planner — 인계를 넘겨 살아야 하므로. §1-1). 근거: helpai에서 마감 뒤 계획을 순차로 돌려 마일스톤 사이 공백이 3h49m이었다. 지시서의 "앞 마일스톤 마감 보고"는 그 시점의 상태 파일·백로그 경로로 대신하고, 마감 결과가 분해를 바꾸면 마감 뒤 delta로 넘긴다.
  - **③ planner일 때만**: 마감·인계 때 계획이 끝나 있지 않으면 기다리지 않는다. 인계 문서에 `계획 진행 중 · pane <id> · agent <이름> · 보고서/계획 문서 <경로>`를 적고 **child가 회수**한다(§9 "진행 중인 worker" 규칙의 예외).
  - (2.3.0) ③을 쓸 수 없어 ① `Agent` planner로 돌렸으면 **인계 전 planner 완료·회수가 필수**다. 마감 뒤 planner를 기다리고 그 대기 분을 "## 시간"(죽은 시간이 아니라 `계획` 칸)에 적는다.
  - 프로젝트가 "Opus 초안 + codex 크로스체크" 같은 자체 계획 방식을 써도 같은 병렬화를 적용한다(초안을 마지막 웨이브 기동 직후 시작).
  - **병렬 planner는 리포의 계획 문서를 직접 고치지 않는다.** 출력은 `/tmp/chain-<chain-id>/plan-draft/`(분해 절·진행 줄 변경안)에 쓰고, 조정자가 게이트·검증이 끝난 뒤(§6 "병행 중 쓰기 금지"가 풀린 뒤) 계획 문서에 옮겨 커밋한다. 마일스톤 Sol 검토 도중 `plan.md`가 바뀌면 snapshot 대조(`sol-review.md` §5)가 깨져 `unverified`가 된다.

## 4. 마일스톤 세션 (조정자)

```text
착수: 인계·상태 확인 → [on-milestone-start] → 사람 필요 항목 일괄 알림(아래) → 진행 보드
wave N:
  task 병렬 기동 (상한 parallel-max, 소유 파일 겹치면 순차) → 진행 감시 기동(§10)
  task 완료 → 보고서 확인 → (authority에 커밋이 있으면) 조정자가 task 파일만 경로 지정 커밋
           → 상태 갱신 → [on-task-done] → 한 줄 보고
웨이브 통합: verify.full 1회 → 고위험 task 묶음 Sol 검토(가벼운 게이트) → BLOCK 수정(기록 줄에 계열 id)
           → [on-wave-integrated] → push (authority에 있을 때) → 진행 보드
마지막 웨이브 기동 직후: 롤링 분해(§3-1) planner 병렬 기동 (2.1.0)
마감 (마지막 웨이브 통합과 합침):
     종료 조건 확인 → verify.full → Sol 최종 검토(§6 게이트 표의 등급별) → BLOCK 수정(기록 줄에 계열 id)
     → [on-milestone-close] → 시각 확인(§6-2) → 롤링 분해 회수(미완이면: ③ pane planner만 인계 문서에 pane·경로를 적고 child가 회수, ① Agent planner는 인계 전에 완료·회수 — §3-1·§9)
     → 마감 체크(아래) → wrap-up·인계 → 진행 보드 → 다음 마일스톤 세션 기동
```

- (2.1.0) **마감 체크**(인계 커밋 전): ① 상태 파일 "## 미해결"에서 해결된 항목을 지운다(결정·근거는 "## 결정"에 남아 있다) ② 상태 파일 frontmatter `updated:`(갱신 줄)를 이번 마감 시각으로 고친다 ③ "## 확인 대기"의 `막힘` 항목 사유가 풀렸는지 본다(§6-2) ④ (2.2.0) "## 시간"에 이번 마일스톤 한 줄을 쓰고 frontmatter `skill:`이 지금 쓰는 버전인지 본다(§8).
- **(2.2.0) 사람 필요 항목 일괄 알림**: 체인 착수(계획 세션)와 마일스톤 착수 때, 계획의 task를 훑어 사람이 해야 하는 항목(로그인, 자격증명·토큰, 승인(push·외부 쓰기·새 비용), 시각 확인, 기기 조작)을 **한 목록으로** 묶는다. 질문 대기열에 `Q<n> [사람]`으로 올리고 `PushNotification`을 **1회** 보낸다(예: `helpai M3 착수: 사람 필요 3건 — 로그인 1·승인 1·시각 1, questions.md Q31~33`). 그 항목에 의존하는 task는 웨이브 뒤쪽으로 배치하고 의존하지 않는 task부터 돌린다. 항목이 하나씩 생길 때마다 따로 알리지 않는다(새로 생긴 항목은 다음 웨이브 착수 때 묶는다. 멈춤 조건이면 §7 멈춤 알림이 따로 간다). 근거: helpai 43.6h 중 사람 대기가 약 1,250분으로 가장 컸다.
  - 사람 대기가 시작되면(그 항목 때문에 진행할 작업이 없어진 시각) 상태 파일 "## 미해결"의 해당 줄에 `대기 시작 <ISO>`를, 풀리면 `대기 끝 <ISO>`를 적는다. "## 시간"의 사람 대기 분은 이 값으로 계산한다.

- 대괄호는 프로파일 훅 절이다. 비어 있으면 공통 동작만 한다.
- 마지막 웨이브의 통합은 마일스톤 마감과 합쳐 검증·일지·push·wrap-up을 한 번만 한다.
- 새 마일스톤 세션은 상태를 승계하고 다음 미완료 작업부터 진행한다. **계획과 계획 검토를 다시 하지 않는다**(롤링 분해 §3-1은 예외).

### worker 기동

- (2.3.0) **기본 ①**: `Agent`(`subagent_type: auto-chain:<worker 등급>`, `run_in_background: true`)로 띄운다. 같은 웨이브의 독립 task는 한 메시지에서 여러 개를 동시에 띄운다. 완료 알림이 오면 그 턴에서 보고서를 회수한다. (2.8.1) 완료 알림·받은편지함 `[worker <task-id>] done|failed` 줄·진행 감시의 `완료` 중 **먼저 온 것**으로 회수한다(나머지가 뒤에 오면 이미 회수했는지만 보고 `--ack`).
- **③ pane**(§1-1 표의 작업만): `references/pane-worker.md` §2~§5(기동 스크립트, 모델 선택, 대화, 완료 감지, 정리).
- 지시서에는 다음만 넣는다. 계획 전문을 붙이지 않는다.
  - 공통 지시서 `references/task-brief.md` 절대 경로 (+ 프로파일 `task-brief`가 있으면 그 경로)
  - 리포 절대 경로, 계획 문서 경로와 task 절 위치(`M1-W1-T03`)
  - 관련 결정 번호·절, 고위험 여부
  - (1.7.0) 마일스톤 `mode`(build|harden)와 task 등급(화면|데이터) — worker의 30분 상한·quarantine 적용 여부가 여기서 정해진다
  - 결함 계열 원장 경로(§6-1)와 이 task에 해당하는 계열 id(조정자가 owns·AC를 보고 고른다. 백로그에 쌓인 계열도 포함. 없으면 "해당 없음")
  - 보고서 경로: `docs/chain/<chain-id>/reports/<task-id>.md`
  - (2.8.1) 조정자 받은편지함 절대 경로(`…/inbox/chain-<chain-id>/coordinator.log`) — ① worker의 완료 한 줄(`task-brief.md` §7)
  - (2.5.0) 쓰기 크기: "한 번의 Write·Edit 출력은 약 150줄·8KB 이하, 더 큰 파일은 뼈대 Write 후 절별 Edit"(`task-brief.md` §3)
- 반환값은 `<보고서 경로> — <결과> <요약>` 한 줄이다(pane worker는 같은 내용을 완료 메시지로 보낸다). 그 이상이 돌아와도 반환 본문을 근거로 쓰지 않는다(확인은 §5 첫 항 — 보고서와 실제 diff).
- 보고서 파일은 조정자의 `Read`·`git commit -- <경로>` 입력이다. 반환된 경로에 파일이 없으면 worker 실패로 보고 §7 실패 처리를 따른다(최종 메시지 내용으로 커밋 목록을 대신하지 않는다).

## 5. 조정자 규율

- **(2.1.0) 확인 범위는 보고서 + 실제 diff + 위험 지점이다.** 조정자는 보고서(결과·실행한 시험·"후속·주의")를 읽고, **보고서와 별개로** 커밋할 경로의 `git diff --stat`과 diff 본문을 직접 연다(보고서에 "주의 없음"이라고 적혀 있어도 연다 — 전역 규칙 "결과는 diff·근거 파일을 직접 열어 확인한다"). diff는 보고서의 변경 파일 목록과 맞는지, 소유 파일 밖 변경·시험 완화·우회가 없는지를 본다. 보고서가 위험·주의로 가리킨 줄은 주변 코드까지 자세히 본다. diff 밖의 worker 코드는 읽지 않고, worker가 통과시킨 시험을 task마다 다시 돌리지 않는다 — 전체 시험 재실행은 웨이브 통합 1회다. 근거: helpai 운영이 이 수준에서 조정자 맥락 18%로 유지됐다.
  - (1.3.1) 예외: **국소 경로(§1)의 BLOCK 수정**은 조정자가 직접 코드를 읽고 고친다. 이때 읽는 범위는 BLOCK이 가리킨 위치와 그 직접 호출자뿐이다. 이 규칙 때문에 국소 수정을 worker로 돌리지 않는다.
- (2.5.0) **큰 파일은 한 번에 쓰지 않는다.** 한 번의 Write·Edit 출력은 약 150줄·8KB 이하로 하고, 그보다 큰 파일은 절 제목과 요지만 담은 뼈대를 먼저 Write한 뒤 절마다 Edit로 채운다(기존 큰 파일을 대부분 고칠 때도 절 단위 Edit). 조정자 자신의 쓰기(상태 파일·보고서·handoff·리뷰 요청·지시서)에 적용하고, planner·worker·breaker 지시서에도 이 규칙을 한 줄 적는다(`references/planning.md` §2-2 나눠 쓰기, `references/task-brief.md` §3). 근거: 한 번에 쓰려다 응답 생성이 시간 초과로 반복되면 파일이 0인 채 수십 분이 간다(훅으로는 못 막는다).
- 계획 문서는 해당 task의 인수 기준과 위험 행만 읽는다.
- 공용 등록 파일(계획의 `조정자 소유` 목록)과 상태 파일·질문 대기열은 조정자만 고친다. worker 보고서의 "조정자 등록 요청"을 반영한다.
- **git index에 쓰는 작업은 조정자만 한다.** 경로 지정 커밋도 index 전체를 잠그므로 worker 여럿이 커밋하면 `index.lock`이 충돌한다. 조정자는 보고서의 변경 파일 목록으로 `git commit -m "<type>(<영역>): <요약> (<task-id>)" -- <경로들>`을 **한 번에 하나씩** 실행한다. 새 파일은 먼저 그 경로만 `git add -- <경로들>`. diff 확인은 이 커밋 전에 §5 첫 항대로 한다.
- `authority`에 로컬 커밋이 없으면 커밋하지 않는다. 보고서와 상태 갱신만으로 통합 검증까지 진행하고, 커밋할 경로 목록을 상태 파일에 누적한다. 이때 Sol 검토 요청과 검증 기록의 snapshot에는 HEAD와 함께 **작업 트리 식별자**(`references/sol-review.md` §2)를 쓴다.
- 보고서의 변경 파일 목록과 `GIT_OPTIONAL_LOCKS=0 git status --short`의 이름 목록이 다르면(목록 밖 변경) 그 파일은 커밋하지 않고 해당 worker 보고서에 질의하거나 질문 대기열에 남긴다. 내용은 읽지 않는다.

## 6-0. 구현 모드(기본)와 출시 검토 (1.6.0)

마일스톤은 기본적으로 **구현 모드**로 진행한다. 목표는 기능을 빠르게 동작시키고 사용자가 눈으로 확인하는 것이다. 출시 품질의 경계 조건 검사는 사용자가 정한 시점의 **출시 검토**에서 한 번에 한다. 근거: giki-ui-refresh에서 되돌릴 수 있는 UI 경계 결함(C5) 하나가 마감마다 BLOCK → 회귀 → 전수 점검(1차 3시간 9분 + 보완 2시간 이상, 해당 세션 보고)으로 이어졌다. 마일스톤마다 전수 점검을 하면 나중에 추가된 화면 때문에 같은 계열을 또 검사하게 된다.

### 구현 모드

- **완료 기준**: 마일스톤 종료 조건(기능 동작) + worker 영향 시험(단위 시험) + `verify.full` + 마일스톤 등급별 마감(§6 게이트 표 — 화면 마일스톤은 Sol 최종 검토 없이 build·스모크). 외부 시스템의 '완료' 반영(진척률 100·완료 전이)은 이 시점에 한다. 전체 QA는 별도 task다. UI 시각검증은 프로젝트 정책을 따른다.
- **바로 고치는 것(BLOCK 범위)**. 아래만 마감을 막는다.
  1. 종료 조건·AC의 주 흐름이 동작하지 않음
  2. 기존 기능 회귀(`verify.full` 실패 포함)
  3. 데이터 손실·권한·보안 오류
  4. 크래시·빌드 실패
  5. 되돌리기 어려운 대상(스키마·배포/보안 설정·계약 문서·비가역 런타임 동작·외부 시스템 쓰기)
  6. 사용자가 시각검증에서 지적한 것
- **미루는 것(백로그)**: 그 밖의 경계 조건(여러 화면 폭, 긴·빈 데이터, 입력 방식 차이, 접근성 세부, 시각 다듬기, 주 흐름이 아닌 드문 경로). Sol은 `NOTE [backlog]`로 올리고, 조정자가 백로그 원장에 적는다. 마감·회차·사다리에 영향을 주지 않는다. 조정자가 고치고 싶으면 다음 task에 묶는다. 재검토 사유가 되지 않는다.
- **전수 점검을 하지 않는다.** 같은 계열이 2회 나와도 §6-1 전수 점검 task를 열지 않는다. 대신 그 계열의 "올바른 모양"을 이후 worker 지시서에 넣어(§4) 새 코드가 같은 실수를 덜 하게 한다.
- **진행 보드**에 `백로그 <n>건 (C5×9, C2×4 …)` 한 줄을 붙인다. 한 계열이 5건 이상 쌓이면 마감 보고에 "출시 검토 시점일 수 있음" 1줄 제안만 한다. 출시 검토를 스스로 열지 않는다.

### 출시 검토

- **사용자가 명시 요청할 때만 연다**("출시 검토해줘", "전체 테스트 진행해줘", 리팩토링·리빌딩 시점). 범위는 체인 전체 또는 사용자가 지정한 영역이다.
- 조정자는 planner에 delta로 `<M>-HARDEN` 마일스톤 삽입을 맡긴다(계획 검토는 가벼운 게이트 1회). 이 마일스톤은 `mode: harden`이고 순서는 다음과 같다.
  1. 백로그 재확인: 이미 고쳐졌거나 없어진 항목을 `fixed`·`dropped`로 닫는다.
  2. 계열마다 한 번 처리한다. 구조로 막을 수 있으면 공용화 + 정적 탐지 + 회귀 시험을 우선하고, 안 되면 §6-1 전수 점검을 한다.
  3. `verify.full`(그리고 프로파일이 정한 전체 시험)
  4. Sol 최종 검토: 무거운 게이트, 출시 기준(§6 BLOCK 정의 전체), 사다리 적용. (1.7.0) `mode: harden` 마일스톤은 등급(화면·데이터)과 무관하게 항상 이 게이트를 쓴다 — planner는 `gate: heavy`로 적는다.
- 출시 검토 중에 나온 결함은 백로그로 미루지 않는다. (1.7.0) 30분 상한(아래)도 출시 검토에는 적용하지 않는다. 상한을 넘긴 문제는 §7 실패 사다리를 따르고, 끝내 못 풀면 그 task를 `blocked`로 두며 출시 검토를 완료로 기록하지 않는다.

### 모드와 무관한 것

- 고위험 task(프로파일 `high-risk`)의 웨이브 Sol 검토, 되돌리기 어려운 대상의 기준은 두 모드가 같다.
- 백로그 원장 경로: 프로파일 `backlog`, 없으면 `docs/chain/<chain-id>/backlog.md`. 조정자만 고친다.

```markdown
| id | 계열 | 위치 | 한 줄 | 출처(게이트·회차) | 상태(open|fixed|dropped) | 닫은 근거 |
```

### 30분 상한 (1.7.0)

근거: 한 문제에 1시간 넘게 붙잡히는 일이 체인마다 반복됐다(사용자가 가장 우려한 지점). 확정 전 화면에 들인 시험·수정은 대부분 버려졌다.

- 적용 범위: 구현 모드(`mode: build`)만. 출시 검토(`harden`)에는 적용하지 않는다(위 "출시 검토").
- **일반 문제**(화면·배치·시험 하니스·간헐 실패·도구)는 한 문제에 30분이 넘으면 멈춘다. 백로그에 `[30분]` 표식과 한 줄(증상·재현·추정 원인)을 적고 다음 task로 간다. §7 실패 사다리도 이 문제에는 체인 중에 돌리지 않는다.
- **미충족 AC 처리**: `[30분]`으로 PARTIAL이 된 task는 원장에 `done`이 아니라 `deferred`(또는 프로젝트 원장의 같은 의미 값)로 두고, 남은 AC를 수정 웨이브 task(`<M>-FIXW-T<nn>`)로 옮긴다. 그 AC가 마일스톤 종료 조건의 **주 흐름**이면 마일스톤을 조건부 마감(§6 "조건부 마감 보고")으로 닫고, 주 흐름이 아니면 정상 마감에 "이월 AC n개"를 적는다. 수정 웨이브가 끝날 때까지 체인 전체를 완료로 기록하지 않는다.
- **간헐 실패**: 단독 재실행에서 통과하면 백로그에 `[quarantine]`으로 올리고 원인을 조사하지 않는다.
- **예외 — 데이터 등급**: 변환기·직렬화·저장 스키마·이관·데이터 손실 카운트 대조·권한은 상한 없이 그 자리에서 해결한다(§7 실패 사다리 적용).
- 백로그의 `[30분]`·`[quarantine]` 항목과 사용자 피드백은 체인 마지막 확인(§6-2) 뒤 **수정 웨이브** 한 번에 묶어 처리한다.

## 6. 검증 예산과 Sol 게이트

### 검증 예산

| 시점 | 실행 | 하지 않음 |
|---|---|---|
| task 완료 | worker가 영향 시험 | 조정자의 재실행 |
| 웨이브 통합 | `verify.static`(있으면) → `verify.full` 1회. 실패하면 원인 task에 수정 worker 1회, 실패 항목과 영향 시험만 다시 | 통과한 항목 재실행 |
| BLOCK 수정 반복 | (2.2.0) 영향 시험 + 재현 회귀 시험만. `verify.full`은 게이트를 닫기 전 1회(§6 "게이트 수렴 규칙" 3) | 회차마다 전체 시험 |
| 마일스톤 마감 | `verify.full` 1회. 같은 snapshot에서 웨이브 통합 결과가 유효하면 재사용 | 증거 시험 처음부터 재실행 |

- 수집 0건, skip, 미실행은 통과가 아니다. 총계를 함께 기록한다.
- 원인을 확인하지 않고 같은 시험을 반복하지 않는다. flaky 의심은 1회만 재시도한다.
- 마감 중에 진행 도구 결함이 드러나도 그 자리에서 도구를 새로 만들지 않는다. 후속 task로 남긴다. 제품 결함은 고친다.
- (1.3.0) 검증·리뷰와 병행하는 동안에는 조정자도 리포에 파일을 쓰지 않는다(작업 트리 청결 검사가 깨지고 snapshot이 흔들린다). 결과 파일·로그는 `/tmp`에 두고 끝난 뒤 옮긴다. (2.1.0) **외부 시스템 반영 도구**(진행 원장·이슈 트래커 동기화 등)가 도는 동안에도 같다 — 원장·상태 파일 커밋을 하지 않는다(office 체인에서 반영 도중 상태 커밋이 섞인 사례).
- **(2.1.0) 검증 snapshot 격리**: `verify.full`이 도는 동안 다음 웨이브 worker를 앞당겨 띄우지 않는다. 앞당겨야 하면 검증을 `git worktree add --detach /tmp/<chain-id>-verify <HEAD>`에서 돌린다. **단 격리는 검증 대상이 전부 커밋돼 있을 때만 쓴다**(`authority.local-commit: yes`이고 `git status --porcelain`이 비어 있음). 미커밋 변경이 검증 대상이면 HEAD worktree는 이전 코드만 시험하므로 격리하지 않고, 검증이 끝날 때까지 worker를 앞당기지 않는다. 이때 worktree에는 gitignore된 데이터가 없어 일부 시험이 skip될 수 있으므로 **collected·skip 총계를 본 작업 트리 직전 결과와 대조**하고, 다르면 그 차이를 기록하고 통과로 세지 않는다. 근거: office 체인에서 검증 중 앞당긴 worker의 미완 변경 때문에 거짓 FAIL 3건과 재실행이 생겼다. 검증 뒤 worktree는 `git worktree remove`로 정리한다.
- (1.3.0) 소요 시간을 말할 때는 실측(로그 생성 시각·mtime·종료 표식)으로 말한다. 참고 문서의 일반 문구("30분 이상 걸릴 수 있다")를 실측처럼 옮기지 않는다.

### BLOCK 수정 지시서 상한 (1.3.0)

worker에게 BLOCK 수정을 맡길 때 지시서에는 **수정 + 재현 회귀 시험 + 영향 시험**만 넣는다. 아래는 같은 지시서에 묶지 않는다(넣으면 한 task가 수정 몇 줄에 1~2시간이 된다).

| 묶지 않는 것 | 대신 |
|---|---|
| 같은 계열 전수 점검표 | §6-1 조건에 걸릴 때 별도 `SWEEP` task |
| 시험 하니스·생성기 확장, 여러 시드 넓은 탐색 | 별도 task(하니스가 정답 조건이 필요할 때만) |
| HEAD 사본 재현 + 가드 제거 사본 여러 개 | HEAD 재현 FAIL 1회만(가드 제거는 고위험 계약 변경일 때 1개) |
| 인접 모듈 시험 전부 | 바꾼 모듈과 그 직접 호출자 시험 |

### 파괴 검토 동시 실행 (1.5.0, 1.7.0부터 기본 끔)

> (1.7.0) 프로파일 `breaker: on`일 때만 아래를 쓴다. 기본은 끔이다. 근거: giki-editor-v2는 breaker 없이 진행했고, 그로 인한 회귀 연쇄는 보이지 않았다. 회차를 줄이는 효과보다 기동·병합 비용이 컸다.

BLOCK 수정이 인접 상태를 새로 깨뜨려 다음 회차에 새 BLOCK이 나오는 연쇄를 한 회차로 줄인다. 수정 커밋 뒤 Sol delta 검토와 `auto-chain:chain-breaker` 서브에이전트를 **같은 snapshot으로 동시에** 띄우고, 둘 다 돌아오면 BLOCK과 파괴 결함을 **한 번에** 고친다. 근거: giki-ui-refresh final-G1 r2 B7·r3 B8은 모두 직전 수정이 만든 C5 회귀였다(r1→SHIP 50분, 그중 회귀 연쇄 23분).

- 구현 모드(§6-0)에서는 breaker 점검표를 §6-0 BLOCK 범위(주 흐름·회귀·데이터/권한·크래시)로 좁히고, 경계 조건 결함은 백로그로 보낸다.
- **발동 조건**(하나라도): ① 같은 계열 2회째 BLOCK ② 직전 BLOCK 수정이 만든 회귀(Sol이 "수정이 만든 회귀"로 판정) ③ 수정이 공유 선택자·공유 상태(스크롤·포커스·이벤트·캐시)·여러 호출자가 쓰는 함수를 바꿈. 첫 BLOCK의 단순 국소 수정에는 쓰지 않는다.
- **적용 게이트**: 무거운 게이트의 BLOCK 수정에만 쓴다(1.7.0). 가벼운 게이트는 재검토가 없으므로 breaker도 띄우지 않는다.
- **순서**: 국소 수정 커밋 → Sol delta 요청과 breaker를 한 메시지에서 기동(breaker는 `run_in_background: true`) → 둘 다 회수 → 합쳐 수정.
  - breaker 지시서: 리포 경로, HEAD, 수정 커밋 sha, 고친 BLOCK id·결과 파일, 결함 계열 원장 항목 id, 영향 시험 명령, 시간 상한 10분, 보고서 경로 `/tmp/<chain-id>-breaker-<게이트>-r<k>.md`.
  - breaker는 리포에 쓰지 않는다. snapshot이 Sol과 같아야 하기 때문이다. 조정자도 둘이 끝날 때까지 리포에 쓰지 않는다(§6 병행 규칙).
- **합친 수정**: Sol BLOCK과 breaker 결함(`K<n>`)을 같은 계열 원장에 함께 분류하고, 한 수정 커밋으로 묶어 고친다(원인이 다르면 커밋만 나눈다). 각 결함의 재현 입력을 회귀 시험으로 넣는다.
  - breaker 결함은 BLOCK이 아니다. 회차를 소모하지 않고 판정을 바꾸지 않는다. 다만 다음 delta 요청의 "확인할 것"에 `K<n>` 해소를 넣는다.
  - Sol이 SHIP이고 breaker 결함만 있으면: 재현으로 확인된 결함만 고치고 커밋한 뒤 delta 검토 1회를 더 받는다(가벼운 게이트면 영향 시험 확인으로 끝낸다). 재현이 안 된 결함은 NOTE로 남긴다.
- **breaker 실패**: 상한 초과·보고서 없음·snapshot 불일치면 그 결과를 버리고 Sol 결과만으로 진행한다. 실패 횟수(§7)에 넣지 않는다. 다음 회차에 다시 띄우지 않는다(같은 게이트당 breaker 실패 1회면 그 게이트에서는 끈다).
- 기록: 상태 파일 "## Sol 검토" 표의 판정 칸에 `breaker K1·K2(C5)` 또는 `breaker 없음`을 붙인다. breaker 보고서는 회수 뒤 `docs/chain/<chain-id>/reviews/`로 옮겨 커밋한다.
- breaker는 Sol을 대신하지 않는다. 게이트 판정은 여전히 Sol의 마지막 `# 판정:` 블록으로만 한다.

### Sol 게이트

실행 절차·요청 형식·리뷰어 선택·결과 판정·장애 처리는 `references/sol-review.md`를 따른다. 이 문서의 "Sol 검토"는 codex CLI(`codex-cli`, Sol high) 리뷰를 뜻한다(2.4.0 단일화). 이어받은 체인의 상태 파일이 `reviewer: opencode-sol|opencode-build`이면 첫 리뷰 전에 codex 드라이런을 통과시키고 `reviewer: codex-cli`로 바꾼 뒤 `## 결정`에 "2.4.0 리뷰어 이관"을 적는다(`references/sol-review.md` §1). 드라이런이 실패하면 대체 리뷰어 없이 원인을 기록하고 멈춰 보고한다.

| 게이트 | 대상 | 조건 | 무게 | 회차 |
|---|---|---|---|---|
| 계획 | 전체 계획 | `review: required` | 마일스톤 2개 이상이면 무거움, 1개면 가벼움 | 3회 / 1회 |
| 웨이브 통합 | 해당 웨이브의 고위험 task 변경 묶음 | 고위험 task가 있을 때 push 전 | 가벼움 | 1회 |
| 마일스톤 마감(화면) | — | (1.7.0) 화면만 바뀐 마일스톤 | Sol 없음 — build·스모크 | — |
| 마일스톤 마감(데이터) | 마일스톤 전체 변경, 종료 조건, 실행 증거 | 데이터·권한·스키마·이관이 들어간 마일스톤 | 가벼움(1.7.0 기본) | 1회 |
| 마일스톤 마감(`gate: heavy`) | 같음 | 계획이 `gate: heavy`로 표시한 마일스톤(저장 스키마·이관 계약을 처음 확정) 또는 `mode: harden` 마일스톤 전부 | 무거움 | 3회 |

- **(2.1.0) 웨이브 고위험 검토를 마감에 합치는 조건**: 같은 마일스톤의 마감 게이트가 **같은 변경**을 본다면 웨이브 Sol을 마감 검토에 합칠 수 있다(push 전 검토가 필요하면 합치지 않는다). 단 저장 스키마·외부 계약 변경이 들어 있으면 마감 게이트를 `heavy`로 올리거나 웨이브 Sol을 유지한다 — 스키마급 변경이 가벼운 게이트 1회로만 검토되는 틈을 막는다. 합쳤으면 상태 파일 "## 결정"에 사유를 적는다.
- **무거운 게이트**: 재검토 요청에 회차(`round 2/3`)를 적는다. 같은 finding이 두 번 연속 나오면 근거를 붙여 1회 반박할 수 있다(회차에 포함). 3회 뒤에도 BLOCK이면 통과로 처리하지 않고 **상한 초과 사다리**로 간다(아래).
- **가벼운 게이트**: 리뷰 1회 → BLOCK 수정 → 영향 시험으로 조정자가 확인 → 재검토 없이 진행. 수정 항목은 마일스톤 최종 검토 범위에 넣는다. 동의하지 않는 BLOCK은 반박 근거와 함께 질문 대기열에 남기고 진행한다. (1.7.0) 단 데이터 등급 finding(조용한 데이터 손실·변환·저장·이관·권한)은 반박으로 넘기지 않는다 — 고치거나, 재현으로 결함이 아님을 보이거나(근거를 상태 파일에 남김), 그 task를 `blocked`로 두고 마일스톤을 완료로 기록하지 않는다. 가벼운 게이트 수정 기록은 `fixed-local <커밋> · <영향 시험 명령·결과>`로 "## Sol 검토"에 적는다.
- BLOCK은 구체적 오동작, 요구 누락, 중대한 회귀, 권한·데이터 오류, 핵심 검증 누락으로 한정한다. 취향·문서 형식은 완료를 막지 않는다. **구현 모드(§6-0)에서는 BLOCK 범위가 §6-0의 6개 항목으로 더 좁아지고, 그 밖은 `NOTE [backlog]`다.** 요청 파일에 `모드: build|harden`을 적는다.
- 리뷰가 진행되는 동안 대상 문서·코드를 고치지 않는다.
- 판정은 실행기 done 파일(유효 조건)과 결과 파일의 `# 판정:` 블록·snapshot이 요청과 같은지로 한다(`references/sol-review.md` §5). `REVIEW-DONE`·로그 문자열만으로는 완료도 통과도 아니다.
- 검토 증거(snapshot, 리뷰 세션 ID, 회차, 판정)를 상태 파일에 기록한다. 검토 뒤에 대상이 바뀌면 바뀐 범위만 delta 검토한다 — 무거운 게이트만(1.7.0). 가벼운 게이트는 `fixed-local` 기록으로 끝낸다.
- **(1.3.0) 재검토는 delta 검토가 기본이다.** 첫 최종 검토(r1)만 마일스톤 전체를 넓게 본다. r2부터의 범위·수렴은 아래 "게이트 수렴 규칙"을 따른다. 요청 형식은 `references/sol-review.md` §2 "delta 요청". 근거: giki-parity M3 최종 검토 8회 BLOCK — 리뷰 실행은 회당 1.5~6분이었고 시간은 수정 주기에 쓰였다.
- 가벼운 게이트의 재검토는 프로파일 `light-gate-rereview`(기본 `none` = `fixed-local` 기록으로 끝)를 따른다. `delta`면 무거운 게이트와 같은 delta 요청을 1회만 받는다.

### 게이트 수렴 규칙 (2.2.0)

근거: 시간을 늘린 것은 리뷰 1회 비용(helpai 43.6h 중 리뷰 실행 ≈240분, 9%)이 아니라 **BLOCK → FIX → 재검토 회차 수**였다. helpai M1-02 r2~r11 MAJOR 15건 중 범위 밖 새 반례 6건, 앞 수정의 "부분 해소" 후속 9건이 회차를 늘렸다. gira는 delta 범위를 고정해 무거운 게이트 r2가 모두 SHIP이었다.

1. **재검토 범위 = 직전 finding의 해소 여부 + 이번 수정이 만든 회귀.** 범위 밖에서 새로 찾은 finding은 심각도와 관계없이 `NOTE [backlog]`로만 받는다. 마감을 막지 않고 회차·사다리를 쓰지 않으며, 조정자가 백로그·후속 task로 넘긴다. **안전 예외**(범위에 따라 조건이 다르다): 범위 **안** finding은 데이터 손실·권한 우회·비가역 변경 위험이면(리뷰어 태그 `[안전]`) 심각도가 MAJOR여도 강등하지 않고 차단한다. 범위 **밖** finding은 같은 위험을 **재현으로 확인**한 경우(`[범위 밖·재현]`, 재현 입력 필수)만 차단하고, 재현 없는 범위 밖 `[안전]`은 `NOTE [backlog]`로 받되 다음 게이트의 확인 항목에 넣는다(원인이 특정되면 국소 경로 §1). `block-on` 매핑의 같은 예외는 `references/sol-review.md` §5-4가 이 규칙을 참조한다.
2. **부분 해소 두 번이면 계열 수정으로 전환한다.** 같은 finding이 `부분 해소`로 두 번 나오면(또는 같은 결함 계열의 BLOCK이 두 번째 나오면 — 위치·증상이 달라도 §6-1 계열이 같으면 센다) 남은 반례를 하나씩 고치지 않는다. 결함 계열(§6-1)의 "패턴·올바른 모양"을 정하고 관련 호출부의 **공통 원인**을 고치는 수정 하나로 바꾼다(국소로 안 끝나면 `chain-worker-xhigh`). 다음 delta 요청에는 "계열 C<n> 공통 원인 수정 — 이전 반례 B<n>…가 모두 닫혔는지"를 확인 항목으로 쓴다. 구현 모드에서도 이 수정은 그 계열의 BLOCK에 대한 것이므로 §6-0 "전수 점검을 하지 않는다"와 충돌하지 않는다(탐지 표 작성 없이 공통 원인만 고친다).
3. **FIX 반복 중 재검증은 영향 시험만.** 수정 → 재검토 사이에는 바꾼 모듈과 직접 호출자의 시험, 재현 회귀 시험만 돌린다. `verify.full`은 그 게이트를 닫기 전(마지막 SHIP 직후 또는 사다리로 넘기기 직전)에 **1회** 돌린다. 실패하면 그 항목만 고치고 영향 시험으로 확인한다.
4. 판정 매핑(`block-on`: MAJOR를 차단으로 볼지)은 `references/sol-review.md` §5-4. 상태 파일에는 원 판정과 실효 판정을 함께 적는다.
- Sol 장애(1회 재시도 후): 웨이브 고위험 검토는 Opus 보조 검토로 진행하고 `sol-pending`을 남겨 최종 검토에 넣는다. 계획 검토·마일스톤 최종 검토는 대체하지 않고 `unverified` + 멈춤 조건 5.

### 상한 초과 사다리 (`authority.escalation`)

무거운 게이트가 3회 뒤에도 BLOCK이면 사용자에게 묻지 않고 `escalation`의 다음 칸으로 간다. 질문 대기열에는 "사다리 n칸 진입"으로 기록만 남긴다. 사다리를 따로 받지 않았으면 기본 사다리 `[extra-rounds:1, carry-reversible, stop]`이다(1.4.0). 이유: 상한 도달마다 멈추면 가역적인 UI 결함 하나로 체인이 사용자 응답까지 몇 시간씩 선다(giki-ui-refresh final-G1 r3 BLOCK → 약 7시간 대기 실측).

| 칸 | 동작 |
|---|---|
| `extra-rounds:<k>` | 같은 방식으로 수정 → 재검토를 k회 더 한다(`round 4/3+2`처럼 적는다) |
| `worker:chain-worker-deep` / `worker:chain-worker-xhigh` | 다음 BLOCK 수정 worker를 그 등급으로 올린다. 재검토 1회. §7 실패 사다리로 이미 그 등급 이상을 썼으면 건너뛴다 |
| `worker:opencode-<agent>` | 다음 BLOCK 수정을 OpenCode `<agent>`(예: `work-sol-xhigh`)로 ② headless 구현한다(2.3.0): `run_in_background` Bash로 `scripts/headless-run.sh opencode:<agent> <worker 지시서(briefs/<task-id>.md, 형식 references/task-brief.md)> <done 파일> <리포>` → `scripts/review-wait.sh <done> <pid>`로 대기(`review-run.sh`는 리뷰 전용). done 파일은 실제 종료 코드·전후 snapshot이고, 완료 판정은 보고서 파일과 diff(§5). 재검토 1회 |
| `carry-reversible` | 남은 BLOCK이 모두 **되돌릴 수 있는 제품 결함**(UI·로컬 코드, 되돌리기 = revert 몇 개)이면 멈추지 않는다. 게이트를 SHIP으로 기록하지 않고 `carried`로 기록한다. 각 finding을 질문 대기열에 "미해결 결함"으로, 다음 웨이브(마지막 마일스톤이면 후속 task)에 수정 task로 올린다. 마일스톤은 **조건부 마감**으로 닫고 마감 보고에 별도 절(아래)을 둔다. 남은 finding에 되돌리기 어려운 대상(스키마·배포/보안 설정·계약 문서·비가역 런타임 동작·외부 시스템 쓰기·main 병합)이 하나라도 걸리면 이 칸을 건너뛰고 다음 칸으로 간다 |
| `stop` | 멈춤 조건 6 |

- 칸마다 진입 시점, 사유(BLOCK id·계열), 결과를 상태 파일 "## Sol 검토"에 적는다.
- 사다리 도중이라도 BLOCK 계열이 전수 점검 조건(§6-1)에 걸리면 §6-1 우선순위대로 처리한다(원인 위치가 특정되면 국소 수정 먼저, 전수 점검은 후속). 전수 점검은 칸을 소모하지 않는다.
- 사다리는 마일스톤마다 처음부터 다시 쓴다. 칸에 없는 행동(새 비용, `authority` 밖 worker)은 하지 않는다.
- **조건부 마감 보고(1.4.0)**: `carry-reversible`로 넘긴 마일스톤은 마감 진행 보드와 인계 문서에 "## 조건부 마감" 절을 둔다. 한도에 닿은 게이트와 회차, 반영한 추천 수정(커밋), 남은 finding(id·계열·한 줄 요약), 되돌리는 비용, 이월한 task id를 적는다. 남은 finding은 이월 task로 반드시 연다. 다음 마일스톤에 Sol 최종 검토가 있으면 그 범위에 넣고, 없으면(화면 마일스톤) 이월 task의 영향 시험을 조정자가 확인하고 그 결과를 "## Sol 검토"에 `carried-check`로 적는다(1.7.0). 사용자 확인 없이 넘어갔다는 사실을 숨기지 않는다. 조건부 마감 뒤 외부 시스템의 '완료' 반영(진척률 100·완료 전이)은 프로파일 훅의 판단을 따른다.

## 6-1. 결함 계열 원장과 전수 점검

같은 종류의 결함이 호출자만 바꿔 계속 나오면 회차가 늘어난다. 이를 막기 위해 BLOCK을 **계열** 단위로 쌓고, 다음 worker와 리뷰에 미리 알린다.

- 경로: 프로파일 `defect-classes`, 없으면 `docs/chain/<chain-id>/defect-classes.md`. 조정자만 고친다.
- 모든 Sol BLOCK(웨이브·최종)과 웨이브 통합 검증 실패를 받으면 계열로 분류한다. Sol 결과에 계열 태그가 있으면 참고하되 판정은 조정자가 한다. 근본 원인(결함을 만드는 코드 패턴)이 같으면 같은 계열이다. 위치·함수가 달라도 같은 계열일 수 있다.

```markdown
## C<n> <계열 이름>
- 패턴: <결함을 만드는 코드 모양 한 줄>
- 올바른 모양: <고친 코드가 따라야 할 규칙 한 줄>
- 탐지: <후보 위치를 찾는 grep·정적 명령. 없으면 "수동">
- 발생: <BLOCK id>(<게이트>, <task>) … — 횟수 <n>
- 전수 점검: 없음 | <task-id> (<결과>)
```

- (1.3.0) 전수 점검은 BLOCK 수정 지시서에 묶지 않는다. 원인 위치가 특정된 BLOCK은 국소 경로(§1)로 먼저 닫고, 전수 점검은 아래 조건일 때 별도 task로 연다.
- (1.3.1) **우선순위**: 같은 계열 2회째 BLOCK이라도 원인 위치가 특정됐으면 그 BLOCK은 국소 경로로 바로 닫는다. 전수 점검 task는 그와 함께 열되 **현재 게이트·마감을 막지 않는 후속 task**다(다음 웨이브 또는 다음 마일스톤 첫 웨이브). 원인 위치가 특정되지 않았을 때만 전수 점검을 먼저 한다.
- (1.6.0) 아래 전수 점검은 **출시 검토(`mode: harden`)에서만** 연다. 구현 모드에서는 계열을 원장에 쌓고 지시서 예방만 한다(§6-0).
- **전수 점검 조건**: 한 계열의 발생이 2회가 되면(게이트·마일스톤이 달라도) 위치별 수정만으로 끝내지 않는다. 전수 점검 task(`<M>-SWEEP-C<n>`, `chain-worker-deep`, 고위험)를 연다. 이 task는 ① 탐지 명령으로 후보 위치를 **모두** 뽑아 보고서에 표로 남기고 ② 위치마다 "올바른 모양" 충족 여부와 근거(파일:줄)를 적고 ③ 위반을 모두 고친 뒤 ④ 계열을 직접 겨누는 시험을 넣는다. 재검토 요청에는 이 표를 실행 증거로 넣는다. 전수 점검 뒤에도 같은 계열이 다시 나오면 §7 실패 사다리를 따른다(새 `chain-worker-xhigh`가 조사+수정, 그래도 실패하면 blocked).
- 탐지 명령을 만들 수 없는 계열이면 전수 점검 task가 먼저 탐지 방법(정적 목록 도구나 시험)을 만든다.
- 원장은 worker 지시서(§4)와 Sol 검토 요청(`references/sol-review.md` §2)에 들어간다. 마일스톤 착수 때 이전 마일스톤의 계열을 다음 웨이브 task의 해당 계열로 미리 고른다.

## 6-2. 시각 확인 (1.7.0)

- 상태 파일 `visual-check`(계획 세션에서 사용자 지시로 정함, 기본 `request`):
  - `request`: 화면이 바뀐 마일스톤 마감 때 바뀐 화면을 사용자 브라우저(프로젝트·전역 규칙의 기본 브라우저 도구)에 **바로 연다**. 응답에는 판·바뀐 점 요약만 쓴다. **기다리지 않고** 화면과 무관한 다음 작업을 진행한다. 다음 화면 작업에 들어갈 때까지 반응이 없으면 넘기고, 상태 파일 "## 확인 대기"에 남긴다.
  - `end`: 중간 요청을 보내지 않는다. 그래도 화면이 바뀐 마일스톤 마감 때마다 "## 확인 대기"에 항목을 쌓는다.
- "## 확인 대기" 항목(두 모드 공통): `M<n> · <화면 이름> · <URL 또는 진입 경로> · <바뀐 점 한 줄> · 상태(대기|막힘(<사유>)|넘김|확인됨|지적)`.
- **(2.1.0) 환경에 막힐 때**: `request`인데 화면을 열 수 없는 사유(서비스 재기동 금지, 로그인 필요, 대기열 질문 미해결 등)가 있으면 `대기` 대신 `막힘(<사유 또는 Q id>)`으로 둔다. 사유가 풀리는 시점(해당 Q 해결 등)에 막힌 항목을 **한 번에 열고** 사용자에게 1회 알린다. 근거: office 체인에서 6항목이 끝까지 `대기`였다가 일괄 `넘김`이 됐다.
- 체인 마지막 마일스톤: "## 확인 대기"를 모두 열어 보이고, 피드백과 백로그(`[30분]`·`[quarantine]`)를 묶어 수정 웨이브를 연다. 그 뒤 **사용자가 확인한 동작만** 회귀 시험으로 고정하는 task를 둔다. 확인 전에는 DOM 세부를 단언하는 시험을 만들지 않는다.
- 피드백이 없으면 추천안으로 진행한다. push·병합·외부 쓰기 승인은 피드백 없음으로 생기지 않는다.

## 7. 결정, 질문, 멈춤

- 확인할 수 있는 사실은 직접 확인한다.
- 기술·설계 선택은 추천안으로 정해 진행하고 이유를 기록한다. 결과가 크게 갈리는 선택도 권한 안이면 추천안으로 진행하고 질문 대기열에 남긴다.
- 정책 충돌, 새 비용, `authority` 밖 작업은 추천안을 대기열에 적고 **그 작업만** 실행하지 않는다. 의존하지 않는 허용 작업은 계속한다.
- 질문 대기열 `questions.md`(상태 파일 옆) 항목: 질문, 추천안, 실제 택한 선택(또는 "대기"), 되돌리는 비용.
- 마일스톤 보고(§10 진행 보드) 때 확인받지 않은 항목만 요약한다. 마감 후 사용자 지시가 없으면 다음 마일스톤 세션을 자동으로 연다.
- **(2.1.0) 멈춤 조건이 아닌 선택지는 기다리지 않는다.** 보고에 선택지를 붙일 때는 `추천안 <x>로 진행 중, 바꾸려면 말씀해 주세요`로 쓰고 바로 진행한다. 질문 형태로 끝내고 응답을 기다리지 않는다. 근거: helpai 마감 보고 뒤 선택지 응답 대기 1h34m.
- **(2.1.0) 반복 질문의 프로파일 반영 제안**: 같은 모양의 사람 판단 질문이 체인 2개 이상에서 같은 답으로 끝났으면, 마감 보고에 "프로파일 `stop-conditions`에 사전 승인 예외 추가" 제안을 1줄 붙인다. 제안일 뿐이며 승인을 자동으로 넘기지 않는다(프로파일 수정은 사용자 확인 뒤).

**멈추는 경우** (이때만 멈추고 보고한다)

1. 남은 작업이 모두 권한 대기나 사용자 결정 대기에 걸려 진행할 독립 작업이 없음
2. 같은 task가 재시도와 조정자의 직접 마무리 뒤에도 실패
3. 다음 마일스톤의 목표를 계획과 상태에서 찾을 수 없음
4. 프로파일 `stop-conditions`에 해당
5. 필수 Sol 게이트(계획 검토, 마일스톤 최종 검토)를 재시도 뒤에도 실행할 수 없음
6. 무거운 Sol 게이트가 3회 뒤에도 BLOCK이고 `escalation` 사다리가 `stop`에 닿음(기본 사다리에서는 되돌리기 어려운 대상이 걸린 BLOCK일 때만)

시간 경과, 침묵, timeout만으로는 멈추지 않는다. timeout이나 빈 응답은 성공으로도 실패로도 세지 않고 `unverified`로 기록한다.

멈출 때는 진행 보드(§10)와 결정이 필요한 질문 id·추천안을 응답에 쓰고, `PushNotification`을 1회 보낸다(예: `giki-parity M3 멈춤: Q21 결정 필요 — 추천 (a)`). 사용자가 자리를 비운 밤 시간에도 대기가 길어지지 않게 하기 위해서다.

### 실패 처리

- (1.7.0) 구현 모드에서는 이 사다리를 **데이터 등급 문제**(§6-0 "30분 상한" 예외 목록)에만 적용하고, 일반 문제는 30분 상한으로 백로그에 넘긴다. 출시 검토(`harden`)에서는 모든 문제에 적용한다.
- **(2.2.0) 실패 사다리 — 원인 모를 실패 1번이면 바로 xhigh에 조사+수정을 함께 맡긴다.** 전역 CLAUDE.md 「원인 모를 실패는 1번이면 바로 Opus xhigh」와 같은 사다리다.
  1. **원인 모를 실패 1번** → 조정자는 두 번째 직접 시도·추가 탐침을 하지 않는다. **새** `chain-worker-xhigh`(pane worker면 opus xhigh) 1개에 **조사와 근본 수정을 함께** 맡긴다(조사만 받고 조정자가 다시 고치는 왕복 없음). 진행 중인 worker가 있으면 멈추고, 그 worker의 미커밋 변경은 **그 worker 보고서(또는 지시서 owns)에 적힌 파일만** 대상으로 필요하면 `git restore -- <그 경로들>`로 걷어낸다. 목록 밖 파일·다른 세션의 변경은 건드리지 않는다(§5).
     - 지시서: 리포·HEAD·건드리면 안 되는 파일 / 재현 명령 / 통과·실패 커밋 / **확인된 사실**(실측값) / **의심 지점**(검증 대상으로 표시) / **반박된 가설 전부**와 각 시도의 보고서 경로 / 금지(증상만 맞추는 수정 — 대기 늘리기·시험 완화·시험 파일 수정·우회) / 확인할 시험 명령 / 보고 형식(원인 파일:줄·메커니즘·확신도·수정 요지·시험 결과·남은 위험).
     - 맡긴 동안 조정자는 같은 문제를 중복 조사하지 않는다(독립 작업은 계속). 돌아오면 바뀐 파일·시험 재실행 1회로 대조하고 "## 결정"에 원인과 채택 근거를 적는다.
  2. **xhigh도 실패** → 그 task를 `blocked`로 두고, 의존하지 않는 작업은 계속하며, 질문 대기열에 반박된 가설 전부와 추천안을 올린다(멈춤 조건 2). 같은 방식으로 다시 돌리지 않는다.
  - 프로파일 `root-cause: sol`이면 1단계 앞에 **Sol 원인 조사**(`references/sol-review.md` §7, 읽기 전용)를 한 번 넣고, 그 안을 들고 xhigh가 수정한다(1.6.2 방식). Sol을 못 쓰면 바로 1단계로 간다. 원인 조사는 게이트가 아니며 회차·판정에 넣지 않는다.
  - 이력: 1.6.2는 "Sol 원인 조사 → 수정 → 새 xhigh → blocked", 1.6.3은 "수정 worker는 처음부터 xhigh"였다. 2.2.0은 전역 규칙에 맞춰 Sol 단계를 선택(`root-cause: sol`)으로 내렸다.
- 여기서 "원인 모를 실패"는 ① worker가 PARTIAL·BLOCKED로 끝나거나 보고서가 없음(원인이 보고서에 특정되지 않은 경우) ② 고쳤는데 같은 증상이 남음(BLOCK 수정 뒤 재검토·웨이브 통합 검증에서 **같은 계열**이 다시 나옴 포함 — task가 달라도 계열이 같으면 이어서 센다) ③ 원인 가설이 빗나감. 세지 않는 것: 오류가 다른 원인을 분명히 가리키는 실패(오타·빠진 import·경로), flaky 의심(1회 재실행), 환경 문제(`index.lock`·포트·오래된 빌드 산출물·API 재시도 반복 — §10 감시), 진단은 맞았는데 구현을 잘못한 실패(구현만 고친다).
- 1.5.0 파괴 검토(breaker)는 수정 뒤 회귀 탐색이라 이 사다리와 별개다.
- xhigh 등급과 Sol 원인 조사는 `authority` 승인이 따로 필요 없다(같은 Claude 서브에이전트 + 읽기 전용 조사). OpenCode worker로 구현을 맡기는 것은 `escalation` 사다리에 있을 때만 한다. 이미 xhigh를 썼으면 사다리의 `worker:chain-worker-*` 칸은 건너뛴다(수정 worker는 처음부터 xhigh이므로 이 칸은 사실상 신규 구현 task가 BLOCK의 원인일 때만 쓰인다).
- 같은 task에서 지시·보고 왕복이 2회를 넘으면 그 task만 조정자가 직접 마무리한다. 두 task 연속이면 질문 대기열에 방식 전환을 제안한다.
- 조정자 커밋 중 `index.lock` 경합(IDE, hook 등)은 구현 실패가 아니다. 잠시 기다려 다시 커밋하고 실패 횟수에 넣지 않는다.
- 반복 실패에 새 가설이 없으면 그 task를 `blocked`로 기록하고, 의존하지 않는 task는 계속한다.

## 9. 인계

- (2.3.0) 다음 세션 기동과 부모 정리는 ③ `references/pane-worker.md` §8(`tab-open "[OC] <한글> M<n+1>"` + `agent-start` + `agent-send --confirm` — 새 세션 첫 지시 **시도 1회**, 재전송 금지)을 따른다. (2.8.0, 2.9.0 4단계) 인계 전에 옛 조정자는 처리한 마지막 번호까지 `--ack` → `inbox-subscribe --unsubscribe` → 인계 문서에 받은편지함 경로·마지막 처리 번호 기록 → 첫 지시 순서를 지키고, 새 조정자는 착수 때 `inbox-subscribe` 뒤 `--pending`으로 n+1부터 처리한다(「세션 간 메시지」). ③을 쓸 수 없으면(10·11·12) 인계 문서만 남기고 다음 세션 시작 명령 한 줄을 사용자에게 보고한다. 전역 인계 규칙(`session-handoff` 스킬)의 Codex 크로스체크는 이 스킬의 Sol 게이트로 대체한다.
- 인계 프롬프트 예: `<상태 파일 절대 경로>와 <인계 문서 절대 경로>를 읽고 auto-chain 스킬로 M<n+1>을 진행해.`
- 진행 중인 worker가 남아 있으면 인계하지 않는다. 회수·정리한 뒤 인계한다. ① `Agent` worker는 예외 없이 인계 전에 회수한다. ③ pane worker만 맥락이 부족해 어쩔 수 없을 때 인계 문서에 pane id·에이전트 이름·보고서 경로와 회수 책임을 적고 넘길 수 있다. (2.1.0) 예외: ③ 롤링 분해·다음 계획 planner는 남긴 채 인계할 수 있다(§3-1).
- 일지는 프로파일 `daily-log` 시점에 쓴다. 매 마일스톤 daily-log+handoff를 이중으로 만들지 않고 상태 파일을 재사용하며, 인계 문서에는 상태 파일에 없는 실행 맥락만 보탠다.
- 맥락이 부족해지면 마일스톤 도중이라도 안전한 지점에서 인계하고 같은 마일스톤을 새 세션이 이어받는다. 진행 중인 worker·리뷰가 있으면 결과 회수 책임을 인계 문서에 적는다.
- **(2.1.0) 조정자 맥락 기준**: 조정자 맥락이 **150K 토큰 미만**이면 "충분"으로 본다(예시 수치 — office 실측에서 200K를 넘은 조정자 세션 3개에 실수가 몰렸다. 인과는 UNVERIFIED. 프로파일에서 바꿔도 된다). 넘으면 웨이브·게이트가 끝난 안전 지점에서 마일스톤 도중이라도 인계한다. 수치를 확인할 수 없으면 추정임을 적는다.
- **(2.1.0) 체인 경계 = 새 조정자 세션**: 체인이 끝난 세션에서 새 체인을 이어서 시작하지 않는다. 새 체인은 반드시 새 조정자 세션(③을 쓸 수 있으면 새 탭 `[OC] …`)에서 연다.

## 10. 진행 보고

체인은 몇 시간씩 돈다. 사용자가 언제 화면을 보더라도 전체 중 어디인지 알 수 있게, 정해진 시점에 짧게 보고한다. 보고는 응답 본문 텍스트로 한다(파일·GUI 아님).

### 진행 보드

상태 파일 "## 마일스톤"·"## 진행"·"## Sol 검토"에서 만든다. 10줄 이내, 아래 형식을 고정한다.

```text
[체인 <chain-id>] M<n>/<총 M> · W<n>/<M의 총 W> · 경과 <h>h<mm>m
M1 ✔ 완료(최종 SHIP r3) | M2 ▶ 마감 중 | M3 · 대기 (1.7.0: 화면 마감은 `M3 ✔ 완료(build·스모크)`, 가벼운 게이트는 `M4 ✔ 완료(Sol 1/1 · fixed-local 2)`)
W2: T03 ✔ DONE · T04 ▶ 2/4 AC 시험 중 · T05 · 대기(deps T04)
게이트: final-M2 r2/3 BLOCK(B8, 계열 C1) → FIX2 진행 | 사다리 0칸 (조건부 마감이면 `M2 ✔ 조건부(carried B9)`)
다음: FIX2 완료 → final-M2 r3 요청
대기열: Q14 대기 | 계열: C1 ×4(전수 점검 M2-SWEEP-C1 예정)
백로그: 12건([30분] 3 · [quarantine] 2) | 확인 대기 2(넘김 1)
```

출력 시점(1.3.1): 마일스톤 착수, 웨이브 통합 끝, 게이트 판정, 사다리 칸 진입, 멈춤, 인계 직전. task 완료는 보드 대신 한 줄 보고로 한다. 이 밖의 시점에는 보드를 내지 않는다. (2.1.0) **인계 직후 이어받은 세션의 첫 응답은 반드시 진행 보드다**(마일스톤 착수 보드와 같다 — 세션별 보드 횟수가 2~23회로 크게 달랐다).

- (2.1.0) 진단·상태 문장(정지 의심, 지연 원인, 소요 시간)에는 근거 종류를 붙인다: `실측`(로그·jsonl mtime·명령 출력) 또는 `화면 추정`. 화면 추정만이면 `UNVERIFIED`.

### 중간 보고 (한 줄)

보드 사이에는 아래 이벤트를 한 줄씩 응답에 쓴다. 형식: `[<chain-id> <M/W>] <대상> <내용>`.

- worker 진행 줄 변경(아래 감시가 알려줌): `[giki-parity M2/W2] T04 3/4 AC · 시험 중 (18분)`

- verify.full 시작·결과(수집·skip 총계 포함)

### 감시 기동

조용히 기다리지 않도록, background로 도는 작업마다 `Monitor`를 하나씩 띄운다. 이벤트가 오면 위 한 줄 형식으로 응답에 옮긴다. Monitor는 최대 30분이므로 만료 알림을 받으면 같은 명령으로 다시 띄운다(작업이 끝났으면 다시 띄우지 않는다).

worker 진행 감시(웨이브마다 1개, 그 웨이브의 task id만 본다. bash 3.2 호환):

```bash
R="<리포>/docs/chain/<chain-id>/reports"; IDS="M2-W2-T03 M2-W2-T04"; S=$(mktemp -d)
while :; do
  left=0
  for id in $IDS; do
    line=$(grep -m1 '^- 진행:' "$R/$id.md" 2>/dev/null)
    [ "$line" = "$(cat "$S/$id" 2>/dev/null)" ] || { printf '%s' "$line" > "$S/$id"; [ -n "$line" ] && echo "$id ${line#- 진행: }"; }
    [ "$line" = "- 진행: 완료" ] || left=1
  done
  [ $left = 0 ] && exit 0
  sleep 20
done
```

Sol 검토는 `references/sol-review.md` §4대로 `scripts/review-wait.sh`를 `run_in_background`로 기다린다(완료 알림이 오면 그 턴에서 바로 판정한다). 경과 줄이 필요하면 같은 절의 Monitor를 함께 띄운다.

- 감시 출력은 진행 알림일 뿐이다. task 완료 판정은 worker 반환과 보고서, Sol 판정은 done 파일과 결과 판정(sol-review.md §5)으로만 한다.
- (2.8.1) **예외**: 감시가 `<id> 완료`를 알렸는데 그 worker의 완료 알림이 아직 없으면 기다리지 않고 그 턴에 보고서로 회수한다(완료 판정은 보고서 `- 결과:` 줄과 diff, §5). 근거: 2026-11-11 완료 알림 유실로 4시간 멈춤.
- (2.8.1) **이 스크립트를 고쳐 쓰지 않는다**(특히 캐시 폴더를 재사용하거나 "바뀐 줄만" 출력하게 바꾸지 않는다). 기동마다 새 `mktemp` 캐시라서 첫 루프가 각 task의 현재 줄을 한 번씩 출력한다. 만료 뒤 다시 띄울 때도 같은 명령이다. **다시 띄운 직후** 첫 출력을 받기 전에 각 보고서 `- 진행:` 줄을 `grep -m1 '^- 진행:'`로 직접 한 번 읽어, 이미 `완료`인 task를 바로 회수한다. 근거: 2026-11-11 grit-portal에서 16:01 재기동 감시가 15:43 완료를 알리지 않아 1시간 20분 늦게 회수했다.
- 웨이브의 worker가 모두 반환했는데 감시가 남아 있으면(worker가 `- 진행: 완료`를 못 쓰고 끝난 경우) `TaskStop`으로 끝낸다.
- 진행 이벤트가 30분 넘게 없으면 그 사실을 한 줄로 보고한다(멈춤은 아니다).

③ pane worker 정지 감시. **③ worker가 있는 웨이브에만** 위 진행 감시와 별개로 웨이브마다 1개를 `Monitor`로 띄운다(① `Agent` worker는 완료 알림이 오므로 띄우지 않는다). (2.2.0) transcript mtime이 아니라 **내용**(마지막 진척 시각·그 뒤 API 재시도 수)과 `agent-status`로 판정한다. 근거: API 오류 재시도도 transcript를 갱신해 helpai M1-09 T5가 99분 동안 코드 0개로 돌았고, mtime 감시는 `blocked`를 알리지 않았다.

```bash
W=$(mktemp)
# 한 줄에 하나: <task><TAB><에이전트 이름><TAB><jsonl 경로|unsupported|빈 값>(spawn-pane-worker.sh 성공 줄의 jsonl=) — 경로의 공백·@를 그대로 둔다
```
