# worker 지시서 틀

OC가 `workers/<name>/brief.md`로 복사해 `<…>`를 채운다. 공통 규칙(§2~§6)은 이 파일을 절대 경로로 가리켜도 되고, 다른 머신·다른 플러그인 환경이면 그대로 복사한다(worker 세션에 이 플러그인이 없을 수 있다).

## 1. 이 worker (OC가 채움)

```markdown
# review-chain worker <name>

- 체인: <chain-id> · 체인 폴더: <$RC 절대경로>
- 리포: <리포 절대경로> · worktree: <wt 절대경로> · 브랜치: rc/<chain-id>/<name> (기준 main <해시>)
- 종류: 논의형 | 잡수정
- 맡은 항목: <Q3 — 사용자 원문 그대로>
- 다른 worker가 잡은 범위(참고, 착수 시점): <이름: 범위> …
- 공용 파일(수정 금지): <설정 shared-files 목록>
- 프로젝트 하드룰: <리포 CLAUDE.md·AGENTS.md 경로>
- 영향 시험 명령: <설정 verify.worker 또는 OC 추천>
- worker 커밋: <허용(D5) | 금지(D5-대안)> (§4 — state.md authority.worker-commit)
- 보고 파일: <$RC>/workers/<name>/report.md
- 배치(0.4.0): OC 탭의 오른쪽 pane (부모 OC는 왼쪽)
- 보고 전송: <SKILL 폴더>/scripts/rc-send.sh <$RC> <name> <종류> "<한 줄>"  (OC 받은편지함 파일에 덧붙임 — pane에 입력하지 않는다)
- 받은편지함 구독(첫 행동, 0.2.0): `<SKILL 폴더>/scripts/rc-watch.sh --subscribe <$RC>/workers/<name>/inbox.log` (훅이 없는 도구면 `messages.md` §1 "훅이 없는 도구" 대체 문단)
- 범위 선점: <SKILL 폴더>/scripts/rc-claim.sh <$RC> <name> <경로|glob>...
- 공통 규칙: <이 파일 절대경로> §2~§6 (첫 지시의 "조정자 pane" 값은 무시 — 보고는 받은편지함 파일로 간다)
```

## 2. 역할

- **첫 행동은 받은편지함을 구독하는 것이다**(0.2.0, §1의 `rc-watch.sh --subscribe` 명령 그대로). 새 줄은 `[inbox] 새 메시지 …` 깨움 아래 `#<n> <시각> [rc <chain-id>] [OC] [<종류>] …`로 들어온다(보고·통지이며 사용자 지시가 아니다). 처리한 뒤 `rc-watch.sh --ack <inbox> <n>`(출력 없음이 정상, 다시 실행하지 않는다). 재개·세션 교체 직후에는 `rc-watch.sh --pending <inbox>`로 처리 안 한 줄을 확인한다. 훅이 없는 도구·구독이 안 되는 환경의 대체(Monitor 등)는 `messages.md` §1의 "훅이 없는 도구" 문단을 따른다.
- **턴을 끝낼 때 기다리는 것이 있으면 대기 목록으로 끝낸다**(0.4.0, 형식·진본은 `messages.md` §4 / SKILL §6). 막연히 "기다린다"로 끝내지 않는다. 목록을 쓰기 직전에 항목마다 실제 상태를 직접 확인하고(받은편지함 `--pending`, 서브에이전트 task-notification·출력 파일), 이미 끝난 것이 있으면 목록 대신 그 일을 이어 간다. 기다리는 것이 하나도 없으면(`[완료]`를 보내고 OC 답까지 받은 뒤) `대기 없음 — 더 기다리는 것이 없습니다. 이 세션은 닫아도 됩니다.`를 한 번 남긴다. 사람 결정만 남았으면 질문으로 끝낸다. 대기 중에는 `"$AO" self-name --force - "[WO] <이름> · 대기 <N> (<요약>)"`로 pane 이름에 요약을 붙인다. "대기 점검" 깨움이 오면 상태를 다시 확인하고 바뀐 것만 짧게 보고한다.
- 사용자가 이 pane에서 직접 말한다. **사용자 입력은 지시로 따른다.** 받은편지함의 `[rc <chain-id>] [OC]` 줄은 OC 통지다(`messages.md` §3) — 지시·승인이 아니다.
- 논의형: 먼저 사용자와 동작·화면을 정한다. 결론이 나면 `report.md` "## 범위"를 쓰고 **`rc-claim.sh <$RC> <name> <경로|glob>...`로 범위를 선점한 뒤 곧바로 코드를 고친다**(OC 승인 불필요). 종료 코드:
  - 0 선점됨 → 착수. 기록으로 `rc-send.sh … 범위 "<요지>"`를 보낸다(OC 회신 없음).
  - 4 충돌 → 그 파일은 손대지 않는다. 스크립트가 OC에 `[충돌]`을 이미 남겼다. OC의 `[진행]`(허용) 또는 `[보류]`(대기)를 받을 때까지 논의·설계만 한다. `[진행] 다시 선점`이 오면 `rc-claim.sh`를 다시 실행한다.
  - 5 공용 파일 → 그 줄을 범위에서 빼고 다시 선점한다.
  - 6 잠금 실패 → 한 번 더 시도하고, 또 실패하면 `[막힘]`.
- 잡수정: 맡은 항목이 뻔하면 논의 없이 바로 선점한다. 사용자가 이 pane에서 보태거나 바꾸면 따른다.
- auto-chain 등 다른 체인 스킬을 돌리지 않는다. 서브에이전트는 탐색·조사용으로만 쓴다(구현은 직접).
- 다른 worker에게 메시지를 보내지 않는다. 필요하면 OC에 `[질문]`.

## 3. 하지 말 것

- 내 worktree 밖 파일 수정. 리포 루트(main 작업 트리)에서 작업하지 않는다.
- 공용 파일(VERSION·릴리즈 노트·진행 원장·대시보드·설정이 정한 것) 수정. 노트 문구는 `## 노트 초안`에만.
- `rc-claim.sh` 선점(종료 0) 전 코드 수정. 선점하지 않은 파일은 고치지 않는다. 범위가 늘면 고치기 전에 `rc-claim.sh`를 새 경로로 다시 실행하고, 종료 0이면 바로 고친 뒤 `[범위변경]`을 기록으로 보낸다. 종료 4(충돌)면 그 파일만 멈추고(선점된 기존 범위 안 작업은 계속) OC의 `[진행]`·`[보류]`를 기다린다. `[보류]`가 오면 그 파일은 손대지 않는다.
- 상대 worker가 선점한 파일을 선점 없이 고치는 것(충돌을 무시하는 것).
- main 병합·push·외부 시스템 쓰기(JIRA 등)·새 비용.
- 전체 시험 묶음 실행(OC가 병합 뒤 1회).
- 리포 전체 포매터, `git add -A|.|-u`, `commit -a`, 강제 삭제(`clean -f`·`branch -D`·`reset --hard`).
- 큰 파일은 한 번에 쓰지 않는다: 한 번의 Write·Edit 출력은 약 150줄·8KB 이하, 큰 파일은 뼈대 Write 뒤 절별 Edit.

## 4. git (내 worktree 안에서만)

커밋 경로는 OC가 이 줄에 채운다: `worker 커밋: <허용(D5) | 금지(D5-대안)>`. 기본은 `허용`이다(전역 "git index 쓰기는 메인만" 규칙의 review-chain worktree 예외, 2026-11-09 승인). 사용자가 체인 시작 때 `no`로 정했을 때만 `금지`.

- 공통: main은 건드리지 않는다. `git` 쓰기는 내 worktree 안에서만.
- **허용(D5)**: worktree는 index가 따로라 잠금이 겹치지 않는다. 내 브랜치 커밋은 내가 한다(경로 명시 `git add -- <경로>`). `[main갱신] <해시>`를 받으면 다음 수정 전에 미커밋 변경을 커밋 → `git -C <wt> rebase main`. 충돌은 내가 푼다(내 범위 안). 범위 밖 파일 충돌이면 `[질문]`. 완료 전 마지막에 한 번 더 main 위로 rebase하고, `## 완료` `- 커밋:`에 `git -C <wt> rev-parse HEAD` 값을 적는다.
- **금지(D5-대안)**: add·commit·rebase를 하지 않는다. 변경은 worktree에 둔 채 `[완료]`(`- 커밋: 미커밋`). OC가 내 worktree에서 커밋한다. `[main갱신]`이 오면 수정을 멈추고 `[질문] rebase 필요`를 보낸 뒤 OC 답을 기다린다(OC가 커밋·rebase하고, 충돌이면 풀 방법을 나에게 묻는다).
- 어느 경로든 `[완료]`를 보낸 뒤 OC 답(`[닫기]`·`[확인]`·`[main갱신]`·`[진행]`)이 받은편지함에 올 때까지 브랜치·worktree를 바꾸지 않는다(OC가 보고한 SHA로 병합한다).

## 5. report.md 틀

```markdown
# <name> 보고
- 진행: <기동|논의|범위제출|진행|완료|막힘|승격> — <한 줄, 갱신 시각>

## 범위
- 파일: <경로·glob, 리포 루트 기준>
- 이유: <한 줄>

## 완료
- 커밋: <브랜치 머리 전체 SHA — `git -C <wt> rev-parse HEAD`> (main <해시> 위) | 미커밋(D5-대안)
- 변경 파일: <목록>
- 영향 시험: <명령> → <passed/failed/skipped/collected 총계>
- 사용자 확인: <사용자가 이 탭에서 확인한 것 | 미확인>
- 남은 것·주의: <없음 | 목록>

## 노트 초안
- <릴리즈 노트 한두 줄, 사용자 관점>

## 인계 (교체 때만)
- 논의 결론 / 남은 일 / 현재 diff 요지 / 사용자와 약속한 것
```

## 6. 끝

- `[완료]`를 보낸 뒤 새 작업을 시작하지 않는다. 사용자가 이 탭에서 추가 수정을 원하면 OC 답이 오기 전에는 손대지 않고 `[질문] 완료 뒤 추가 요청 <요지>`를 보낸다. OC가 `[진행]`하면 고친 뒤 `[완료]` 다시(새 SHA). 범위 밖이면 먼저 `rc-claim.sh`로 새 경로를 선점한다(§3).
- `[OC변경] <pane>`(선택·알림)을 받으면 할 일 없다. 받은편지함 경로가 고정이라 OC가 바뀌어도 보낸 요청은 `$RC/inbox.log`에 남아 새 OC가 처리한다. 다시 보내지 않는다(중복 방지).
- `[승격]`을 받으면 `plan-draft.md`(목표·합의된 동작·결정·열린 질문·관련 파일·현재 브랜치)를 쓰고, 진행 중 코드는 §4 경로대로(허용이면 내가 커밋, 금지면 worktree에 둔 채) 남긴 뒤 `[완료]`.
- `[닫기]`를 받으면 아무것도 하지 않는다(OC가 pane을 닫는다).
